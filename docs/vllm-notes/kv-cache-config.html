get_kv_cache_configs()见vllm/v1/core/kv_cache_utils.py。 逐代码解析：

python
def get_kv_cache_configs(
    vllm_config: VllmConfig,
    kv_cache_specs: list[dict[str, KVCacheSpec]],
    available_memory: list[int],
) -> list[KVCacheConfig]:
    """
    Generates the KV cache configurations for a model.
    Since we use a shared centralized controller for all workers, we need the
    `kv_cache_config` to be consistent across all workers to make sure
    the KV cache allocation can be applied to all workers. However, different
    workers may have different memory available, and different type of layers
    (when pipeline parallel is enabled). To handle the difference between
    workers, the current implementation is:
    1. Merge the KV cache specs of all workers to get the KVCacheSpecs for
       the whole model.
    2. Generate the KV cache groups based on the layer ratio of the whole model.
       This also handles spec unification for hybrid models.
    3. Handle auto-fit max_model_len and memory checks using per-worker
       projected groups to account for PP sharding.
    4. Generate the KV cache configs for each worker based on the KV cache
       grouping strategy. (This is reasonable because the layer ratio of
       different PP stages are similar.)
    5. Change the num_blocks of each worker to the smallest among all workers
       and shrink tensor sizes proportionally to avoid allocating unused memory.

约束：

  • 集中式控制器（Scheduler）：vLLM 的调度器运行在主进程，它维护着一张全局的 block_table（逻辑块到物理块的映射）。这就要求所有 Worker 的 KV 缓存物理块数量（num_blocks）必须完全一致，否则调度器无法用统一的索引去寻址不同 GPU 上的显存。

  • 分布式差异（PP 引入的复杂性）：在流水线并行（PP）中，模型被按层切分（如 GPU 0 负责 1-10 层，GPU 1 负责 11-20 层）。这意味着不同 Worker 持有的层类型和数量可能不同，进而导致内存需求不同。与此同时，不同 GPU 的剩余显存也可能不同。

关于layer ratio，是指混合模型中不同注意力机制的BLOCK的比值，通常在排列BLOCK时是将各种注意力类型的BLOCK大致均匀排布，这样PP分得的不同注意力的BLOCK的比值也可以大致接近（和PP的BLOCK数量和混合模型的排布有关系）。基于这种事实，可以为PP的Worker设计统一的KV cache配置。

  1. 合并所有Worker的KV chache规格，获取完整模型的规格
  2. 基于完整模型里不同类型层的数量比例，把它们归入不同的“缓存组（KVCacheGroup）”。对于非标准规格采取规格统一化处理。
  3. 将全局分组投影到每个Worker上，并根据实际的内存做auto-fit（调整max_model_len）
  4. 基于分组策略为每个 Worker 生成具体的 KVCacheConfig
  5. 统一块数为全局最小值，并等比收缩张量，避免内存浪费。所有Worker的num_blocks（分页缓存的逻辑块）要统一。

具体的划分策略见后续代码。

    # Merge the KV cache specs of all workers. Different PP stages may have
    # different layer names, and different TP ranks of the same PP stage should
    # have the same KV cache spec.
    merged_kv_cache_specs: dict[str, KVCacheSpec] = {}
    for kv_cache_spec_one_worker in kv_cache_specs:
        for layer_name, layer_spec in kv_cache_spec_one_worker.items():
            if layer_name not in merged_kv_cache_specs:
                merged_kv_cache_specs[layer_name] = layer_spec
            else:
                assert merged_kv_cache_specs[layer_name] == layer_spec, (
                    "The KV cache specs for the same layer are different "
                    "across workers. This is not supported yet."
                )

    # `may_override_num_blocks` in `get_kv_cache_config_from_groups` clamps

                avail_mem // bytes_per_block,
                override,
            )
            adjusted_memory.append(override * bytes_per_block)

KVCacheConfig的核心结构： num_blocks：每个Worker上每层可用的物理块数，也是kv_cache_tensors的第一个维度。每个Worker上每层的物理块数是相同的，Worker之间的物理块数num_blocks也是相同的。 kv_cache_tensors: list[KVCacheTensor]：一个张量描述符列表。每个描述符定义了一个需要实际分配的显存块（Tensor），它包含了该张量的大小（size）和被哪些层共享（shared_by）的信息。 kv_cache_groups: list[KVCacheGroupSpec]：原始的分组信息。它告诉 Worker 哪些层属于同一个缓存组，方便后续寻址。

page/block：它是一块固定大小的连续显存空间，用来存放固定数量 Token的 KV Cache 数据。vLLM 默认一个 Page 存放 16 个 Token 的 KV Cache。 page_size_bytes：一个 Page 实际占用的显存大小（字节数），如page_size_bytes = 2 × block_size × num_kv_heads × head_size × dtype_size，block_size是每个 Page 存放的 Token 数量，系数2是K和V。

get_kv_cache_config_from_groups见vllm\v1\core\kv_cache_utils.py，返回KVCacheConfig对象。

  1. if len(kv_cache_groups) == 1 and isinstance(kv_cache_groups[0].kv_cache_spec, UniformTypeKVCacheSpecs) 即所有layer的注意力缓存类型相同，计算出每个layer分配的page或者说物理块数量（num_blocks）（可分配内存除以每个layer的page_size_bytes之和），再根据每个layer自身的page_size_bytes计算各自的内存大小，为每一层创建各自的张量（张量i的大小为num_blocks * layer_i.page_size_bytes），这样可以保证每层的物理块数一致，方便管理。
  2. _use_packed_kv_cache_config(vllm_config, kv_cache_groups) 紧凑布局，为deepseek等模型的配置。简单来说就是默认布局是这样的：token0~15的layer1的KV cache储存在一个块，layer2的KV cache也存在一个块，以此类推。而紧凑布局将token10~15在所有layer的KV cache中都打包存在一个块，可以降低传输开销，降低管理成本等。
  3. else ：即一般情形。block_table即逻辑块是按group缓存组来分开管理的，也就是可以说每个group有自己的block_table，在此基础上，general情形下，我们取所有group里最大的layer数为group_size，创建group_size个张量（KVCacheTensor）。每一个张量的大小为num_blocks * page_size_bytes，其中num_blocks是每个Worker上每个张量可用的块数（可以等价于所有组的相同 层一起的物理块数），它是由available_memory//(group_size*page_size)得到的。在此基础上，所有group的第i个layer存放在张量i上（即相同索引位置的layer共享物理内存），具体储存在哪个物理块上由请求决定，最后通过逻辑块寻址。
python
    # Change the num_blocks of each rank to the smallest among all ranks.
    # We also need to shrink the tensor size proportionally to avoid
    # allocating unused memory.
    min_num_blocks = min(
        kv_cache_config.num_blocks for kv_cache_config in kv_cache_configs
    )
    for kv_cache_config in kv_cache_configs:
        num_blocks_old = kv_cache_config.num_blocks
        kv_cache_config.num_blocks = min_num_blocks

        # Shrink tensor size proportionally
        for tensor in kv_cache_config.kv_cache_tensors:
            assert tensor.size % num_blocks_old == 0
            tensor.size = tensor.size // num_blocks_old * min_num_blocks

        if len(kv_cache_config.kv_cache_groups) > 0:
