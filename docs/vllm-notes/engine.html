各文件职责 ​

文件 核心类/内容 职责
__init__.py EngineCoreRequest, EngineCoreOutput, EngineCoreOutputs, FinishReason, PauseMode 等 跨模块共享的数据结构定义，是整个 engine 包的基础
exceptions.py EngineGenerateError, EngineDeadError 异常类型定义
detokenizer.py IncrementalDetokenizer 增量 detokenization，逐 token 解码输出文本
logprobs.py LogprobsProcessor 处理 log probabilities，生成 SampleLogprobs / PromptLogprobs
parallel_sampling.py ParentRequest 管理 n>1 的并行采样请求，将父请求拆分为多个子请求并聚合结果
input_processor.py InputProcessor 将 EngineInput → EngineCoreRequest，处理 tokenization、多模态、LoRA 等
output_processor.py OutputProcessor, RequestOutputCollector 将 EngineCoreOutputs → RequestOutput，内部依赖 detokenizer、logprobs、parallel_sampling
tensor_ipc.py TensorIpcSender, TensorIpcReceiver, TensorIpcData 跨进程零拷贝张量传输（通过 torch.multiprocessing.Queue）
coordinator.py DPCoordinator, DPCoordinatorProc 数据并行（DP>1）时的协调进程，负责负载均衡统计和 DP wave 同步
utils.py CoreEngineProcManager, CoreEngineActorManager, EngineZmqAddresses 启动/管理 EngineCore 子进程或 Ray Actor，ZMQ 地址管理
core.py EngineCore, EngineCoreProc 推理核心循环：调度器 + 执行器，是真正执行模型推理的地方
core_client.py EngineCoreClient, InprocClient, SyncMPClient, AsyncMPClient 前端与 EngineCore 通信的客户端抽象，支持进程内/同步多进程/异步多进程三种模式
llm_engine.py LLMEngine 同步推理入口（向后兼容），供离线 LLM 类使用
async_llm.py AsyncLLM 异步推理入口，供在线 API server 使用

依赖关系图 ​

关键分层说明 ​

底层（数据/工具层）

  • __init__.py 定义所有跨模块数据结构，几乎被所有文件依赖 1
  • exceptions.py 定义两种异常：可恢复的 EngineGenerateError 和不可恢复的 EngineDeadError 2
  • tensor_ipc.py 提供跨进程零拷贝张量传输，被 core.py 和 core_client.py 使用 3

中间层（处理层）

  • detokenizer.py + logprobs.py + parallel_sampling.py 是 output_processor.py 的内部依赖 4
  • input_processor.py 独立处理输入，不依赖其他 engine 子模块 5

核心层（执行层）

  • core.py 的 EngineCore 是真正的推理内循环，包含调度器和执行器 6
  • core_client.py 的 EngineCoreClient 封装了与 EngineCore 的通信，InprocClient（进程内）/ SyncMPClient（同步多进程）/ AsyncMPClient（异步多进程）三种实现 7
  • coordinator.py 仅在 DP>1 时使用，协调多个 DP rank 的请求波次 8

顶层（入口层）

  • llm_engine.py 的 LLMEngine 是同步入口，供离线 LLM 类使用 9
  • async_llm.py 的 AsyncLLM 是异步入口，供在线 API server 使用 10

分层解析 ​

1. tensor_ipc.py ​

simple and navie knowledge ​

  • IPC：进程间通信，用于在不同进程间传递数据。传统的pickle通过序列化和反序列化的方式传递数据（优势是能够处理复杂的数据），而tensor_ipc.py实现零进程拷贝张量传输（优势是能够处理大张量），具体做法是先将数据放入共享内存空间，通过传递元数据的方式进行数据传递。

  • 前后端场景：前端即 TensorIpcSender 所在之处，负责对接受的原始信息进行预处理。（如离线推理的LLM类，逻辑上的前端）；后端即 TensorIpcReceiver 所在之处，负责对接受的原始信息进行后处理，或者说进行实际的模型计算和GPU占用。（如离线推理的EngineCore，逻辑上的后端）

  • OOB: Out-of-Band，即带外运输，是指数据传递的设计模型，控制信号和数据分别走对应的通道（queue和shared memory）。

Sender ​

首先组装元数据，将tensor存入共享内存tensor = tensor.share_memory_()，然后将元数据入列queue.put(ipc_data, timeout=10.0)。

Receiver ​

由于Sender发送的数据可能因为线程调度异步到达，因此Receiver设计了一个Drain-and-Buffer策略。

具体来说，当后端请求张量时，先从self._tensor_buffers中查询元数据，如果没有，就循环从queue中获取元数据，并存入self._tensor_buffers，直到找到需要获取的元数据。

接收端的数据过滤 ​
  • 请求端将已有的小于当前请求message_id的对应缓存数据删掉，避免无效占用

    sender.current_message_id = message_id  # 更新为 5
return tensor
