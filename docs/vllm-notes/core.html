EngineCore：核心循环与初始化 ​

EngineCore、EngineCoreProc、DPEngineCoreProc 的架构，以及执行器、KV Cache 和调度器的初始化。

core.py ​

架构 ​

core.py 定义了 vLLM v1 引擎的最内层执行循环，包含三个层层递进的主要类：

  • EngineCore —— 核心推理循环：拥有一个 model_executor: Executor（模型执行器）、一个 scheduler: SchedulerInterface（调度器）以及一个 structured_output_manager（结构化输出管理器）。它不包含任何网络层，设计用于进程内使用（InprocClient）或被 EngineCoreProc 包装后跨进程运行。core.py:103-145
  • EngineCoreProc —— 将 EngineCore 包装在后台进程中，为其添加基于 ZMQ 的输入/输出套接字线程，使其能够通过 IPC（进程间通信）与 EngineCoreClient 的具体实现进行交互。
  • DPEngineCoreProc —— 继承自 EngineCoreProc，专用于数据并行（DP>1）部署。它在各 DP 等级之间增加了运行/暂停状态的全规约（All-Reduce）同步机制，并负责“请求波次”（Request Wave）的协调。

依赖关系 ​

关键导入项展示了 EngineCore 所依赖的核心组件：

  • vllm.v1.core.sched.interface.SchedulerInterface / vllm.config.get_scheduler_cls() —— 可插拔的调度器。
  • vllm.v1.executor.Executor —— 抽象模型执行器（管理 GPU/Worker）。
  • vllm.v1.core.kv_cache_utils（包含 get_kv_cache_configs, resolve_kv_cache_block_sizes 等）—— KV 缓存大小计算与配置。
  • vllm.v1.structured_output.StructuredOutputManager —— 语法/结构化解码的状态管理。
  • vllm.v1.engine.tensor_ipc.TensorIpcReceiver 以及 vllm.v1.engine.utils（包含 EngineZmqAddresses, EngineHandshakeMetadata）—— 为进程间通信变体提供 IPC/ZMQ 底层支持。
  • vllm.v1.serial_utils（包含 MsgpackDecoder/MsgpackEncoder）—— 基于 ZMQ 传输的请求/输出（反）序列化。
  • vllm.v1.fault_tolerance.engine_core_sentinel —— 用于工具调用的容错包装器。core.py:46-93

核心方法 ​

  • 初始化（EngineCore.__init__）：创建执行器（Executor），随后调用 _initialize_kv_caches()。该方法会查询 model_executor.get_kv_cache_specs()，通过性能分析调用 determine_available_memory() 确定可用显存，计算 get_kv_cache_configs()，并调用 model_executor.initialize_from_config() 完成配置；最后构造 self.scheduler。core.py:106-160

  • step()：单次推理迭代 —— 调度器执行 scheduler.schedule() 选取批次，模型执行器运行 model_executor.execute_model() 执行前向传播（返回一个 Future[ModelRunnerOutput]），随后调度器调用 scheduler.update_from_output() 将结果转换为 EngineCoreOutputs。

  • add_request()：将预处理后的请求（Request）交给 self.scheduler.add_request()。

  • 生命周期辅助方法：sleep()/wake_up() 用于暂停调度器，并执行执行器 GPU 状态的卸载/恢复；shutdown() 释放 model_executor 和 scheduler；collective_rpc() 将 RPC 调用转发给所有执行器 Worker。

  • EngineCoreProc 的补充机制：运行两个后台线程 —— 一个输入线程负责解码 ZMQ 请求并将其转换为 EngineCoreRequest 并进行预处理，另一个输出线程负责将 EngineCoreOutputs 编码后通过 ZMQ 发送回去。它们围绕 run_busy_loop() 运转，该循环持续清空输入队列，调用 step_fn（即 step() 或 step_with_batch_queue()），并将结果推入输出队列。

  • DPEngineCoreProc.run_busy_loop() 的补充机制：发布请求计数统计信息用于负载均衡，并定期执行全规约（通过 ParallelConfig.sync_dp_state）以同步各 DP 等级的“是否存在未完成请求”/暂停状态。当所有 DP 等级均进入空闲状态时，发送 wave_complete 通知。

如果有KV cache规格标记了非因果注意力，就要禁用chunked prefill和prefix caching。

Chunked Prefill（分块预填充） 是一种优化，它将长 Prompt 分块处理，以提高吞吐量。但该优化假设注意力是因果的（因为分块时需按顺序处理）。非因果注意力无法分块，因此必须关闭。 Prefix Caching（前缀缓存） 依赖于对连续 token 序列的哈希索引，且假设相同前缀的注意力模式是一致的。非因果注意力会破坏这一假设，因此也要禁用。

get_kv_cache_configs()见vllm/v1/dore/kv_cache_utils.py及get_kv_cache_config.md。

其主要流程：

  1. 合并所有 Worker 的 KV cache 规格，得到完整模型的统一视图
  2. 将相同/兼容规格的 layer 归入缓存组（KVCacheGroup），并处理混合模型的规格统一化
  3. 将全局分组投影到每个 Worker（考虑 PP 切分），按需 auto-fit max_model_len，并检查内存是否充足
  4. 通过 get_kv_cache_config_from_groups() 为每个 Worker 生成 KVCacheConfig（计算 num_blocks 和 kv_cache_tensors）
  5. 统一所有 Worker 的 num_blocks 为全局最小值，等比收缩张量大小避免浪费内存

python
def generate_scheduler_kv_cache_config(
    kv_cache_configs: list[KVCacheConfig],
) -> KVCacheConfig:
    """
    Generate the KV cache configuration for the scheduler.
    """
    assert all(
        [cfg.num_blocks == kv_cache_configs[0].num_blocks for cfg in kv_cache_configs]
    )
    # All workers have the same kv_cache_config except layer names, so use
    # an arbitrary one to initialize the scheduler.
    cfg = copy.deepcopy(kv_cache_configs[0])
    for group in cfg.kv_cache_groups:
        if isinstance(group.kv_cache_spec, UniformTypeKVCacheSpecs):
            # All layers in the UniformTypeKVCacheSpecs have the same type,
            # so use an arbitrary one to initialize the scheduler.
            group.kv_cache_spec = next(
                iter(group.kv_cache_spec.kv_cache_specs.values())
            )
    return cfg

1.4 self.structured_output_manager ​

python
self.structured_output_manager = StructuredOutputManager(vllm_config)
1

结构化输出管理器（StructuredOutputManager）是 vLLM 推理引擎中负责强制模型输出符合预定义结构的核心组件。它的核心功能是通过约束解码技术（guided decoding），确保大语言模型（LLM）的生成内容严格遵循用户指定的格式（如 JSON Schema、正则表达式、固定选项等），从而避免自由生成导致的格式错误问题。
