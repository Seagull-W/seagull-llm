1. 研究对象与证据链 ​

这是 2026 年 9 月公开展示的 MiMo-V2.6 Pro/Flash RL 运行。官方发布明确回顾了六天 Live RL；训练看板公开了逐步指标、评分结果、运行状态和团队公告。罗福莉 X 原帖直接读取失败，因此不将转载的全文当作已核验原话。

最有价值的四类材料是：运行中的指标与公告、发布后的重复工具调用诊断、开源复现代码与任务数据、用户 Issue。它们能串起实际闭环，但开放程度不同。

训练指标来源：Flash 序列、Pro 序列。指标定义来源：看板元数据。avg@n 不是“n 次至少成功一次”的 pass@n，也不能等同于 rollout 的平均数值 reward。

DeepSWE 采用 mini-swe-agent，avg@3。Flash 从第一步到最后一步增加 17.01 个百分点；Pro 增加 14.16 个百分点。这是归档内 step 1 对 step 30 的比较，step 1 已是训练步，不是未训练基线。Flash 最高值为 step 28 的 67.86，最后一步不是最高点。Pro 26、30 步均为 72.57。评测归档

同一归档还包含 In-house Coding Bench 和 AutomationBench v1.0.6，均标为 avg@3。Pro 这两项的最后公开点为 step 29，不应补成 step 30。全部结果见 离线评测 CSV。

不能做的因果解释 ​

  1. 移除 cyber 和筛简单题会改变训练指标的统计总体，前后 reward 不能作为纯粹的能力差。
  2. 最后一次 live 采样器步数可以超过 30；采样器准备下一批不意味着 optimizer 做了第 31 次更新。
  3. 沙箱计数远高于轨迹数，不能直接解释为不同训练题数，也不是 GPU 数。
  4. 异步流水线的 rollout 与 trainer 用时可能重叠，不能简单相加再推 GPU 利用率。
  5. 评测缺点和波动不构成失败原因证据；需要对应 checkpoint、样本及评分日志。

9B 的定位必须先确认 ​

MiMo-V2.6-Distill-Qwen-9B是基于 Qwen3.5-9B、使用 MiMo 生成数据的 SFT 起点，用于继续做 RL。它本身不能当作完成开源 RL 的结果，更不能当作直播中的 Pro/Flash。技术报告中的单域 RL 表格也不是一个同时获得全部单域成绩的统一 checkpoint。

6. 上线后的反馈闭环 ​

发布后出现重复工具调用反馈。官方在 09-27 给出诊断：原训练把单轮工具调用的惩罚触发上限设为 32，这可能放大未触发阈值的重复行为。针对性缩小上限的试验有效，但把这一修复放进完整任务混合需要很高成本，随后采用专门教师及 MOPD 修复。官方诊断

官方的重复率按单轮内规范化 JSON 工具调用去重计算，未覆盖跨轮和近似重复；所报告样本来自筛选/回放实验，不能当作全部线上流量发生率。MOPD 修复回滚五步后加入教师指导，报告约 9 万美元开销；API 于 09-25 北京时间 06:00 更新，模型名称保持一致，因此只记 API 名无法定位行为版本。同一诊断

Issue #98是重复调用的用户反馈入口；Issue #102报告修复后对有效多工具调用可能过度抑制。这些都是应纳入回归测试的行为线索，不是已独立验证的普遍结论。

7. 本案例带来的可执行问题 ​

以下是整理建议，适合转成自己训练的验收项：

  • 错误分类漏检时，能否从样本定位到被影响的 optimizer 更新，并明确回滚边界？
  • task、grader 和 harness 是否独立版本化，修分类规则后是否回放旧样本验证？
  • MoE 负载指标是否与 OOM 的 rank、层、阶段对应，改变并行策略后是否重新检查数值一致性？
  • 调整任务难度后，是否保留固定评测集和任务分布快照？
  • 限制重复调用时，是否同时测试正常连续工具使用，防止过度抑制？

本项目需要继续追踪的原始材料列在 未公开项。目前最关键的缺口是生产运行 resolved config、全部重启日志、错误样本/评分记录和各次并行调整参数。
