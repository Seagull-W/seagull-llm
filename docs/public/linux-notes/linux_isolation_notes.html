02 · 基础概念

程序、进程与线程

程序是存储的代码；进程是执行中的程序实例，拥有 PID（进程标识符）、虚拟地址空间、文件描述符等资源；线程是进程内部的执行单元，同一进程中的线程通常共享地址空间。

同一个程序可以对应多个进程；PID 仅为示例。

Shell、内核与系统调用

Shell（例如 Bash）解析用户命令并启动程序；内核负责进程调度、内存管理、文件系统及网络等；系统调用（syscall）是用户态程序请求内核服务的入口，例如 read、write、openat。

echo $$                              # 当前 Bash 的 PID
ps -p $$ -o pid,ppid,stat,comm      # PID、父 PID、状态、名称
cat /proc/$$/status                 # 查看 Bash 的进程状态

/proc 是由内核提供的虚拟文件系统，不是普通磁盘资料库。它能展示进程及内核信息，也暴露部分控制接口。

03 · Namespace：隔离资源视图

Namespace 决定一个进程如何“看见”某些资源。隔离环境中的进程仍然使用同一个 Linux 内核。

类型被隔离的资源/视图
pid进程 ID 空间；同一进程可在嵌套 PID Namespace 中有不同 PID
net网络接口、路由、端口空间等网络栈资源
mnt文件系统挂载点视图
uts主机名、NIS 域名
ipcSystem V IPC 与 POSIX 消息队列等
user用户/组 ID 映射及 Namespace 范围内的能力
cgroupcgroup 路径的呈现视图（不等于资源限制本身）
time部分单调/启动时钟的偏移视图

隔离视图（示意）

init · PID 1
python · PID 2

需要配置相应 PID、UTS Namespace 及 /proc 挂载

Namespace 可以改变进程看到的标识与列表，而非复制整套内核。

查看现有 Namespace

ls -l /proc/self/ns/
readlink /proc/$$/ns/pid
readlink /proc/1/ns/pid

符号链接例如 pid:[4026531836] 中的数字表示 Namespace 对象的 inode；同类型 Namespace 的编号可用于比较进程是否处于同一个 Namespace。/proc/self 会指向访问路径的进程自身。

创建隔离主机名的 Shell

# 尝试进入独立 USER + UTS Namespace
unshare --user --map-root-user --uts bash

# 在新 Shell 内执行
hostname demo-container
hostname
exit

# 回到原 Shell 再检查
hostname

成功时，只改变新 UTS Namespace 内可见的主机名。--map-root-user 将当前用户映射为新 User Namespace 内的 root，不等于宿主机 root。

环境限制：某些 Ubuntu 版本、AppArmor 配置、云主机策略会禁止无特权 Namespace 创建；出现 Operation not permitted 不表示命令写错。不要为做实验而关闭主机安全策略。

04 · cgroups：按组管理资源

Control Groups（控制组）把进程组织成层级，并由内核控制器对进程组进行资源统计、分配与限制。现代 Ubuntu 多使用 cgroup v2 统一层级。

和限制策略

限制通常作用于归属该 cgroup 的整组进程，而不是某个程序文件。

常见控制项：cpu.max 控制 CPU 带宽配额，memory.max 设置内存硬上限，pids.max 限制任务数量。CPU 的 50% 配额通常意味着相对于一个 CPU 核的半个核心持续使用量，而不是“整台多核机器总量的 50%”。

只读观察（安全）

cat /proc/self/cgroup       # 当前进程属于哪个 cgroup
stat -fc %T /sys/fs/cgroup # 若输出 cgroup2fs，即使用 cgroup v2
cat /sys/fs/cgroup/cgroup.controllers

systemd 如何使用 cgroups

systemd 可通过服务配置设置资源限制。例如以下为示意配置，不是让你直接修改已有服务：

[Service]
CPUQuota=50%
MemoryMax=1G
TasksMax=128

要点：Namespace 主要决定“看见哪些资源”；cgroups 决定“组内消耗多少资源”。即使没有 Namespace，也可以对普通系统服务使用 cgroups。

05 · seccomp：过滤系统调用

seccomp（secure computing）是 Linux 的系统调用过滤机制。常用的 seccomp-BPF 允许进程装载过滤规则，根据系统调用号及参数进行判断，并触发允许、拒绝（如返回错误）、终止、记录或用户态通知等动作。

用户态进程调用 openat() / mount()
↓
seccomp 规则检查 根据调用号 / 部分参数做判断
↙              ↘
允许

进入后续内核处理

拒绝或处理

返回错误 / 终止 / 通知等

示意流程：真实过滤结果由具体规则、内核支持及其他安全策略共同决定。

例如，容器运行时可能禁止某些不必要的内核操作。但 seccomp 不理解文件路径的语义；它无法单凭过滤规则完成“只允许访问 /workspace 文件”的路径级权限管理，这通常还需要文件系统隔离、权限、LSM（如 AppArmor）等机制。

查看当前进程 seccomp 状态

grep -E '^(Seccomp|Seccomp_filters):' /proc/self/status
Seccomp 值含义
0未启用 seccomp
1严格模式（仅允许极少数系统调用）
2过滤模式（seccomp-BPF）

只读状态无法告诉你具体过滤规则。seccomp 通常由容器运行时或沙箱启动器在进程启动阶段设置；单靠 grep 无法判断某个系统调用会否被允许。

两个隔离环境仍共享同一个 Linux 内核；上图只表示可能的隔离配置。

容器不是虚拟机：典型 Linux 容器共享宿主机内核；虚拟机则通过虚拟硬件运行独立的客户机操作系统及内核。容器启动通常较轻量，但隔离强度取决于具体配置。

安全边界不是单一功能：实际沙箱还常使用 Linux capabilities、用户与文件权限、只读挂载、根文件系统隔离、AppArmor/SELinux、网络策略等。三个机制不会自动阻止所有越权行为。

与 Codex / Agent 的关系：工作目录权限、网络可达性与 CPU/内存限制属于不同维度。不能仅凭“网络被禁止”断定一定是 seccomp 导致，也不能仅凭“工作区不可写”断定使用了 Namespace；具体原因需要检查实际沙箱实现和配置。

07 · Ubuntu 命令速查

想检查什么命令
当前 Bash PIDecho $$
进程及父进程ps -p $$ -o pid,ppid,stat,comm
当前进程信息cat /proc/$$/status
Namespace 列表ls -l /proc/self/ns/
比较 PID Namespacereadlink /proc/$$/ns/pid
当前 cgroup 归属cat /proc/self/cgroup
cgroup 文件系统类型stat -fc %T /sys/fs/cgroup
seccomp 状态grep '^Seccomp' /proc/self/status
观察系统调用（需 strace）strace -e trace=openat,read,write cat /etc/hostname
创建 USER + UTS Namespace（可能被策略禁止）unshare --user --map-root-user --uts bash
实验边界：以上以只读检查为主。别在正在运行 Hermes、Codex、Mihomo 的生产环境上随意修改现有 cgroup、seccomp、AppArmor 或 systemd 服务配置。

一句话记忆：Namespace 管“看见什么”，cgroups 管“使用多少”，seccomp 管“允许请求内核做什么”。
