给一个训练步计时 ​

测一次训练步的墙钟时间，起点是主机准备提交这一步，终点是这一步的 GPU 工作全部完成。假设主机提交任务后就读时钟，而 GPU 仍在执行，那么这段时间只能告诉我们提交有多快。要测整步耗时，需要在两次读时钟之间等待设备完成。

先确定一步里包含哪些运算。同一个模型可以按三种模式运行。forward 在无梯度模式下只做前向；for_bac 再计算损失和反向传播；full 还执行 AdamW 更新。计时输入是预先在设备上生成的随机 token，模型构建和数据读取都在计时区间外。

在 benchmark.py 里，预热结束时先同步。进入正式测量后，每步都等 GPU 完成再记录主机耗时，单位为秒。脚本默认 batch 为 4、上下文为 512、测量 10 步，small 配置有 128,625,408 个参数。报告记录的是本地单卡结果。

t0 = timeit.default_timer()
step()
torch.cuda.synchronize()
times.append(timeit.default_timer() - t0)

时钟在调用前启动，等同步返回才停止，所以 Python 调度、GPU 执行和主机等待都算在这一步里。第 6 讲用 CUDA 事件读的是设备流里两个事件的间隔。第 6 讲 · CUDA 事件计时

运行一次前向计时

数据来源为 A2 的 write_up.md，计时逻辑位于同目录的 benchmark.py。在配置好作业 GPU 环境后，可分别调整下例中的预热次数。

uv run python benchmark.py --model-size small --mode forward --context-length 512 --batch-size 4 --warmup 1 --num-steps 10

固定前向计算，改变预热次数 ​

先只运行 small 模型的 forward，保持输入、模型和测量步数相同，只改变正式计时前预热几步。下表是这组实验留下的单卡记录。想看一步平均跑多久，读均值。想看十步之间差得多不多，读标准差。变异系数把标准差除以均值，方便比较不同配置下的相对波动。

预热步数均值（秒）标准差（秒）变异系数
00.1450290.11038876.1%
10.1102750.0011861.1%
20.1100910.0005480.5%
50.1097150.0002420.2%

以第一行为例，0.110388 ÷ 0.145029 ≈ 0.761，所以变异系数为 76.1%。这个数描述十步耗时的相对波动。预热一步后，标准差降到 0.001186 秒，用同样的算法得到约 1.1%。

从 0 次到 1 次预热，均值下降约 35 毫秒；再增加一次，均值只变了约 0.18 毫秒。这个差别可能来自第一步的额外开销。原表只记录了汇总值，还分不清开销来自初始化、缓存，还是其他因素。

固定预热次数，加入反向传播 ​

测过前向之后，再把反向传播和优化器更新逐步加回来。三种模式都先预热 5 步，再计时 10 步。表中沿用作业记录的数值。

模式small 均值（秒）small 变异系数medium 均值（秒）
forward0.1097150.2%0.335881
for_bac0.37237211.3%12.009977
full0.4013140.5%15.529772

small 的前向加反向这一组波动最大，完整训练步却只有 0.5%。各模式是分开跑的。两行均值相减，只能粗估多出来的耗时，没法据此找出哪个 kernel 最慢。medium 从前向到前向加反向，耗时从约 0.34 秒升到约 12 秒。要解释这次变化，还得对照同一次运行的硬件利用率、显存压力和时间线。

进程启动与预热 ​

前后程序的warmup是否会相互影响？

后续可把冷启动和进程内稳态分开测。用多个新进程轮换运行 0 次和 1 次预热的配置，保存每一步的原始时间，同时记录温度、频率及其他负载。比较各进程的首步与后续各步，可以检验这项猜想。原作业没有记录这项对照的结果。
