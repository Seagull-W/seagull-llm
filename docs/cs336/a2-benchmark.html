一次训练步到底怎么计时 ​

你量的是提交任务，还是 GPU 做完一整步？CUDA 异步执行，step() 返回时 GPU 可能才开始。主机时钟读时间，torch.cuda.synchronize() 等当前设备先前提交的工作完成。

benchmark.py 先建模型、AdamW 和设备上的随机输入，再预热、计时。默认 B=4、T=512、V=10000；[B,T] 输入变成 [B,T,V] logits，展平为 [BT,V] 求标量 loss。创建与数据准备不计时。

for_bac前向 + loss + backward()源码不清梯度，预热和测量持续累加 .grad
full再加 optimizer.step() 与 zero_grad(set_to_none=True)清梯度也计时，下一步重新产生梯度
benchmark.py · benchmark() 的实际计时与汇总
with nvtx.range('warmup'):
    for _ in range(warmup):
        step()
    torch.cuda.synchronize()  # flush warmup work before the clock starts

times = []
for _ in range(num_steps):
    t0 = timeit.default_timer()
    step()
    torch.cuda.synchronize()
    times.append(timeit.default_timer() - t0)

# main() 中
mean = statistics.fmean(times)
std = statistics.stdev(times) if len(times) > 1 else 0.0

print("RESULT_JSON\t" + json.dumps(result, allow_nan=False))

timeit.default_timer() 使用高分辨率单调时钟；time.time() 是可能受校时影响的日历时间。墙钟包含 Python 调度、GPU 执行和同步等待；CUDA 事件只读设备流内的间隔，但提交不及时造成的设备空闲也可能落在区间里。

RESULT_JSON\t{...} 含配置、统计量和逐步 times。run_benchmarks.py 每组启动新进程，却未把 times 导出 CSV，需另存 JSON。进程隔离分配器，不重置温度、频率和外部负载。

预热把哪些工作搬出了时钟 ​

预热要走正式测量的路径。docstring 的四类机制如下；本地没有逐项耗时，不能各填一个毫秒数。

混合精度：范围够不够，累加准不准 ​

范围与精度要分开看。下表按格式定义计算，u 为舍入到最近值的相对误差界；有效位含隐含首位 1。

格式指数 / 尾数字段（有效位）u最大 / 最小正正常数
fp328 / 23（24）2⁻²⁴≈5.96×10⁻⁸3.403×10³⁸ / 1.175×10⁻³⁸
fp165 / 10（11）2⁻¹¹≈4.88×10⁻⁴65504 / 6.104×10⁻⁵
bf168 / 7（8）2⁻⁸≈3.91×10⁻³3.390×10³⁸ / 1.175×10⁻³⁸

mixed_precision_accumulation.py 从零开始加 1000 次 0.01。write_up 的四个打印值依次为 10.0001 / 9.9531 / 10.0021 / 10.0021，理想实数答案为 10。

  • fp32 加 fp32：加数表示与反复舍入都有微小误差，所以打印为 10.0001。
  • fp16 加 fp16：10 在 [8,16) 中，相邻可表示数的间距（ulp）为 2³⁻¹⁰=0.0078125。它小于 0.01，但已同量级；这一段每次加法可能只前进一个台阶，误差并非均匀随机抵消，最终为 9.9531。
  • fp32 加 fp16：0.01 在 fp16 中为 1311×2⁻¹⁷=0.01000213623046875，乘 1000 得 10.002136…，解释 10.0021。这里这些和可被 fp32 精确表示，主要误差就是加数的量化。
  • 先 fp16 再转 fp32：转换保留已舍入的值，不会恢复原来的 0.01，所以仍为 10.0021。0.009765625 不是 fp16 的最近表示。

手算保守上界：和在 [0,16) 时，每次舍入至多 0.00390625，加上输入误差，|误差|≤1000×(0.00390625+0.00000213623)≈3.9084。该界也保证中间和小于 14，区间自洽。记录误差约 −0.0469，远小于上界；紧估计要逐次舍入，不能假设所有误差同号最大。

autocast 改的是算子，不是整张模型 ​

沿 ToyModel 区分计算与存储类型：假设 CUDA、模型和输入初始 fp32、autocast 目标 fp16、交叉熵 loss。以下为规则推导，非实测。

ToyModel 按 fc1→ReLU→LayerNorm→fc2 执行，末维先变 10，再变类别数。AMP 算子规则让矩阵乘降精度利用 Tensor Core，softmax/layer_norm/exp/log 走 fp32。cat/stack 按输入类型提升；不能混用 CPU 与 CUDA 的白名单，未列算子不保证升 fp32。

对象类型与理由
参数fp32；上下文没有调用 model.half()，原参数存储不变
fc1 输出fp16；linear 采用低精度计算，ReLU 沿用输出类型
LayerNorm 输出fp32；CUDA autocast 对 layer_norm 选择 fp32
logitsfp16；fc2 的 linear 再次选低精度
lossfp32；cross_entropy 走 fp32 策略，不是所有 loss 都自动如此
参数梯度fp32；叶子参数的 .grad 与 fp32 参数匹配，不是因为 loss 恰好 fp32

backward 在上下文外沿前向选定类型反传，并非全用 fp32；optimizer.step() 的参数与状态更新也不应被自动转换包住。fp16 范围小，常需梯度缩放；bf16 范围近 fp32，但只有 8 位有效位，累加、相消更敏感。

benchmark 的 --autocast 选 bf16。速度对照本地未测；可用 hook 检查层输出与参数梯度 dtype，再同协议测开关，16 位不保证两倍快。

归一化为什么单独照顾 ​

归一化输出小，不保证中间统计量安全。write_up 的 RMSNorm 注释说：“manually upcast the input to fp32 here to prevent overflow when you square the input”，并链接 pytorch#66707。

# write_up.md · RMSNorm.forward，先转换，再平方
in_dtype = x.dtype
x = x.to(torch.float32)
rms = torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + self.eps)
x = x * rms
return (self.weight * x).to(in_dtype)

手算 √65504≈255.94，256²=65536 已超 fp16 范围。激活若为 1～10，平方并不越界；危险在异常值或低精度求和：1024 个 10 的平方和为 102400，均值虽为 100，先累加可能溢出。实际内核是否高精度累加须另查。

bf16 平方阈值约 1.84×10¹⁹，通常够用。但 LayerNorm 的 (x−μ)/√(σ²+ε) 在 x≈μ 时会放大已有舍入误差；RMSNorm 不减均值，仍有累加。两者统计量都宜用 fp32，却救不回已量化的输入。本地未测；用大幅值、近常数输入，对照 fp64 输出和梯度验证。

显存账：激活从哪里来 ​

激活是为反向留下的中间张量。每层 residual 为 [batch,seq,d_model]；L 来自层数，c 汇总 QKV、MLP、归一化等保存项，b 为每元素字节数。

按 benchmark 的 xl 配置 d=2560、L=32，题设 B=4、T=2048、fp16：单个 residual 为 4×2048×2560×2=41943040 字节，即 40 MiB；每层各留一份就是 1280 MiB=1.25 GiB。手算示例取 c=10，仅线性规模激活便为 12.5 GiB，这不是实测峰值。朴素注意力还另有 B×H×T² 项：H=32 时单份 fp16 分数矩阵就有 1 GiB/层，不能藏进与 T 无关的常数。

峰值常在反向初期：保存的激活未释放，新梯度已产生，优化器状态仍驻留。AdamW 的 m/v 各 fp32，共 8 字节/参数；参数与梯度另算。首次 step() 创建状态也可能是峰值，须测量判定。

混合精度省低精度激活和计算权重，通常省不到 fp32 优化器状态。autocast 不改变原参数存储；显式半精度权重也可能另留 fp32 主权重，总账不能减半。

本地未测：怎样留下可检查的显存证据
  1. 固定 xl 与 context=128/2048，分别准备 forward/full、全精度/bf16 运行；区分首次更新与稳态。
  2. 按 PyTorch 显存记录文档，调用 torch.cuda.memory._record_memory_history()，同步并重置峰值，再执行待分析步骤。
  3. 同步后记录 torch.cuda.max_memory_allocated()，调用 torch.cuda.memory._dump_snapshot("snapshot.pickle")；下划线接口需核对安装版本。
  4. 在 memory_viz 打开快照，以分配栈判断大张量来自哪里、反向何时释放。它只看到 PyTorch 分配器管理的内存，NCCL 等外部分配需另查。

剖析：把时间花在哪 ​

剖析将总时间定位到代码。外层 range_push('forward'/'backward'/'optimizer') 标阶段，内层 nvtx.range 标 scores、softmax、final matmul：QKᵀ 从 […,T,dₖ] 生成 […,T,T]，PV 回到 […,T,dᵥ]。

脚本 monkeypatch cs336_basics.model.scaled_dot_product_attention，把标注留在测试脚本，不改库；仍需验证掩码、缩放与 softmax 等价。mask 位于 scores 与 softmax 范围之间，也属注意力成本。

待验证时可运行 nsys profile --trace=cuda,nvtx,cublas,cudnn -o trace python benchmark.py --model-size small --mode full。在 NVTX 轨道定位主机调用，再沿 CUDA API 的关联找设备 kernel；范围结束不代表 GPU 已完成。读汇总要同时看调用次数与平均时长，总时长≈次数×均值；时间占比的分母是所选 kernel 总时长，不一定是墙钟。并发区间不能重复相加，SM 占用率也不是这个占比，细查通常需 Nsight Compute。本地尚无可据此归因的完整记录。

算术强度（arithmetic intensity）是 FLOPs/搬运字节数。手算单头 scores：约 2BT²d 次浮点运算；若只计 Q、K 读取和分数写出，强度≈2T²d/[b(2Td+T²)]。T 增大时它趋向 2d/b；只拿 2BT²d 除以 BT²，两项的 T² 会抵消，不能声称该比值随 T 增长。softmax 对每个分数只做少量运算，却需多遍读写，强度通常低。足够大的矩阵乘较可能受计算限制，softmax 较可能受带宽限制；长序列物化 T² 张量加重访存压力，但整段注意力究竟受哪一项限制仍需测量。

剩下的作业：先把理论账推通 ​

这里把手册 §3 之后的题面变成可复算的模型：以下均为理论推导，本地未实现。激活检查点先说明取舍：每 k 层存一个边界，反向重算块内激活，粗略存储为 A(L/k+k)；求导得到 k≈√L。xl 的 L=32，手算最优量级约 6 层，实际还受张量大小与块边界影响。验证须对照无检查点的梯度，并测 k=4、6、8 的峰值和重算时间。

FlashAttention：边看分块，边维护 softmax

对一块查询维护逐行最大值 m、指数和 l、未归一化输出 O。新键块给出分数 S=QKᵀ/√d；旧和原本按旧 m 缩放，换最大值后必须同步缩放 l 与 O：

初始 m=−∞、l=0、O=0，结束后逐行除以 l。手算一行分两块，分数 [0, ln2]，值 [2,4]：第一块 m=0、l=1、O=2；第二块 m=ln2，旧贡献乘 1/2，得 l=1.5、O=5，输出 10/3，正好等于 (1×2+2×4)/3。

大小为 Bq×Bk 的分数块临时存储 O(BqBk)，另有 O(Bqd) 累加器；固定块大小和 d 后无需保存整张 T² 矩阵，QKV、输出及逐行统计量总存储 O(Td)，对 T 为线性。反向重算分块概率，FA2 还优化并行调度；仅有上述递推不等于完成 FA2。验证须将分块输出、logsumexp 与朴素实现对拍，再比 dQ/dK/dV，覆盖因果掩码和大分数，并扫描 T 验证峰值增长。

DDP：带宽账之外，还有启动账

分布式数据并行（DDP）各卡保留全参数，反向后平均梯度。设 N 卡、每卡完整梯度 G 字节、有效链路带宽 β；环状 all-reduce 拆成 reduce-scatter 与 all-gather，各传 (N−1)G/N：

α 是每轮启动延迟。手算示例：1 亿个 fp32 参数的梯度 G=0.4 GB，N=4、β=25 GB/s，忽略启动项得 0.024 s。若分成 K 个参数张量单独通信，带宽总量近似不变，启动项却乘 K；展平或分桶可摊薄它，分桶还能与反向重叠。验证需用各 rank 的不同数据，对照单进程全局 batch 更新，检查平均而非求和，再固定总字节数改变张量数量测耗时。

ZeRO-1 / FSDP：到底切掉哪份副本

取明确的 fp32 账本：参数 4、梯度 4、AdamW 的 m/v 共 8，即每参数 16 字节。设参数数目 P，DDP 每卡 16P；ZeRO-1 只切状态，为 8P+8P/N；完全分片数据并行（FSDP）把三类一起切，理想持久存储为 16P/N，尚未计激活和临时 gather 缓冲。

手算 P=1 亿、N=4：三者每卡为 1.6、1.0、0.4 GB（十进制）。ZeRO-1 各卡更新所负责参数后还要同步新权重；FSDP 则在计算前 all-gather 权重，梯度产生后 reduce-scatter。手册规定前向后释放完整权重，因此一整步通常是前向 gather + 反向 gather + 梯度 reduce-scatter，不能简化成每步只有两次集合通信。

沿用 G=0.4 GB、N=4、β=25 GB/s，并假设权重与梯度同字节数：每次 gather 或 reduce-scatter 的带宽项为 0.012 s，三次合计 0.036 s；DDP 的两阶段为 0.024 s。实际逐层启动、预取重叠与低精度通信会改账。验证要对照单卡参数更新，覆盖共享权重、参数组和多步迭代；分别量初始化、更新前后峰值，并用时间线确认完整权重及时释放、通信先于使用完成。

本篇要点 ​

协议先于数字：固定形状与边界，预热后同步，逐步计时并保存 times。预热表支持首次路径与稳态有别；medium 的异常比例提示补采显存和时间线，还没有给出原因。

下一次只改一个因素：查慢在提交、内核还是分配迁移，误差在量化还是累加，显存由谁占住。用公式估量级，用记录区分假设；未运行的 FA2/DDP/FSDP 仍是理论账。
