词元为什么从字节开始 ​

字节级分词要解决的问题，是怎样覆盖新文本又控制序列长度。词元（token）是分词器交给模型处理的基本单位，它可以对应一个字节，也可以对应多个字节。字节对编码（Byte Pair Encoding，BPE）从基础符号出发，把高频相邻符号合成新符号，从而缩短序列。

起点收益代价
词级常用词只占一位词表大，新词与无空格语言需另处理
字符级易复用，切分直观有限表仍有未登录字符，字符不等于视觉字形
字节级固定 256 个基础符号，覆盖全部字节值序列长，靠合并压缩

train_bpe.py · train_bpe 以 {i: bytes([i]) for i in range(256)} 建立基础词表，覆盖 00–FF 全部字节。UTF-8 是把文字编码成字节序列的方式，因此这张表能够表示所有合法 UTF-8 文本。“你”等常见汉字占 3 字节 E4 BD A0，而部分扩展汉字占 4 字节，所以一个字符并不总是一个基础词元。

这里把压缩率定义为每个词元平均承载的字节数，也就是上式中的字节数除以词元数。“你好”有 6 字节，如果编码成 6 个字节词元，比值就是 1；如果每字对应一个词元，比值便是 6/2 = 3。空文本的分母为零，这个比值没有定义。素材未提供 GPT-4 分词器测量值，因此这里仅用手算例子说明口径。

词表大小、序列长度和压缩率之间存在一个三角权衡。设词表大小为 V、嵌入宽度为 d，把每个词元映射为向量的嵌入表就需要 V×d 个参数；当 d=768 时，V=10k 对应 7,680,000 个参数，V=50k 对应 38,400,000 个参数，两者相差 30,720,000 个参数。对于同一段文本，更高的压缩率意味着更短的词元序列，但通常要用更大的词表容纳这些组合。设序列长度为 T，在其他条件固定时，标准全注意力中两两交互的计算量随 T² 增长，因此缩短序列能降低这部分成本，却会增加词表侧的参数开销。

词表保存 ID → bytes 的映射，其中 ID 是模型用来索引词元的整数编号；合并表则保存按执行优先级排列的字节对。假设词表里同时有 ab 和 bc，那么 abc 既可能切为 [ab,c]，也可能切为 [a,bc]。即使词表还有 abc，编码器也必须按规则顺序决定如何合并，不能只凭最长匹配选择词元。

预分词先定边界 ​

预分词先把文本切成片段，再限定相邻符号能够合并的范围。预分词（pre-tokenization）是正式合并之前的切分步骤，它既缩小搜索范围，也规定不同片段之间永远不合并。你可以把片段边界当作隔板：后面的统计和替换都只能在隔板内部进行。

片段边界如何确定 ​

tokenizer.py · Tokenizer.encode 的 PAT 是定义切分规则的正则表达式，它按从左到右的顺序尝试六个分支。表达式使用 Unicode 属性来识别字母和数字，因此需要支持这些属性的 regex 库，不能直接换成标准库 re。下表把每个分支单独列出来，读代码时还要结合它们的先后顺序判断匹配结果。

分支匹配含义与例子
'(?:[sdmt]|ll|ve|re)缩写后缀：we're → we / 're；区分大小写，'RE 不走此分支。
?\p{L}+可选的一个空格加连续字母（含汉字）。hi there 得到 hi、 there。
?\p{N}+可选空格加连续数字类别字符；a12 分成 a、12。
?[^\s\p{L}\p{N}]+可选空格加连续非空白、非字母、非数字字符，如 ?!。
\s+(?!\S)空白后不能是非空白；文末全吃，词前多空格回退，留一个给后词。
\s+兜底剩余空白，如制表符、换行。

这个规则会把一个空格粘在后一个词前面，使词前边界保留在片段里。因此，word 与 word 能够学到不同表示。遇到 a b 时，切分结果是 [a, 空格, 空格+b]，因为空白分支会回退，给后一个词留下一个空格。这里的负向前瞻，也就是只检查后续内容而不消耗字符的条件，并不只匹配文末空白。

这套规则把数字与字母分开，但不阻止 1 与 2 合成 12。原因是数字分支里的 + 允许连续数字留在同一个片段中，这与 GPT-2 的 encoder.py · Encoder.__init__ 一致。如果你希望逐位隔离数字，就必须另改正则，不能指望后面的合并过程自动划出边界。

本地 train_bpe.py · train_bpe 的 PAT 在数字分支前夹有换行和缩进，却没有启用忽略格式空白的模式。这些空白因此成为匹配条件的一部分，已有实测中 12 没有匹配。训练函数应与编码器共享同一条写成一行的正则，避免训练漏掉数字。本页的字母手算示例不受这个缺陷影响。

defaultdict(int) 是缺失键默认从零开始的计数字典，这里用它记录每种片段出现的次数。例如，(b'a',b'b',b'a'): 3 表示这个字节片段出现了 3 次。列表可以修改，不能作为字典键；元组及其中的字节元素可以哈希，也就是能够计算用于字典查找的散列值。不过，长度为 n 的元组在构造和哈希时仍需 O(n) 的工作，并不是没有成本。

手算两轮合并 ​

我们用两种预分词片段手算合并，检查每轮的频数与选择结果。这个示例包含 aba × 3 和 aca × 1，每个片段内部才允许出现相邻对。下表记录两轮合并前后的贡献，你可以逐行核对哪些对消失、哪些对新出现。

当前相邻对初始贡献第一轮后第二轮后
(a,b)3 × 1 = 300
(b,a)3 × 1 = 300
(a,c)1 × 1 = 111
(c,a)1 × 1 = 111
(a,ba)03 × 1 = 30

初始语料共有 3×2+1×2 = 8 对，每个三字节片段贡献两个相邻位置。(a,b) 和 (b,a) 同为 3 票，作业“Compute BPE merges”要求在频数并列时取字节字典序较大的对，这就是这里的并列裁决（tie-break）规则。元组比较先看左项，因为 b'b' > b'a'，所以第一轮选中 (b,a)。train_bpe.py · train_bpe 中的 max(candi_list) 实现的就是这条规则。

第一轮合并后，语料变为 [a,ba] × 3 和 [a,c,a] × 1，相邻对总数降为 5。新出现的 (a,ba) 有 3 票，胜过各 1 票的 (a,c) 和 (c,a)。第二轮因此得到 [aba] × 3 和 [a,c,a] × 1，只剩后一个片段里的 2 对。

BPE 每一步只选择当前最高频的相邻对，这是一种只看眼前收益的贪心策略（greedy strategy），并不保证全局最优压缩。前一步会改变后续可见的相邻对，因此早期选择的差异可能一直传递到最终词表。tiktoken、GPT-2 和本作业采用的具体训练约定并不必然相同，边界规则或并列裁决不同，都可能让它们在同一语料上得到不同词表；如果语料、规则和所有约定完全相同，贪心本身并不会凭空引入随机性。

遇到重复字符时，你要区分相邻对的计数和实际可替换的位置。aaa 的位置 0–1、1–2 都是 aa，所以计数为 2，但中间的 a 不能被重复使用。源码从左替换后执行 i += 2，因此只得到 [aa,a]。这说明统计次数不等于非重叠替换次数。

第一轮合并后，a 的右邻居已经变成 ba。旧 (a,b) 的 3 票随之失效，不能继续留在候选频数里。训练器必须更新受影响片段的相邻对，否则下一轮可能选出当前序列中根本不存在的组合。

增量更新与词表编号 ​

训练循环必须同步更新相邻对频数，并为新词元分配连续编号。这里的增量更新，是只扣除受影响片段的旧贡献，再加入它们的新贡献。频数维护回答下一轮该选谁，编号维护则保证新合成的字节串有可供编码器查询的 ID。

train_bpe.py · train_bpe 用片段频次给每个相邻位置加权，再从累计结果中取最高频对。同一个片段只保存一份字节序列，但它出现多少次，每个相邻位置就要贡献多少票。下面的原实现通过 pretoken_freq[key] 取得这个权重，因此统计的不是去重后片段的数量。

for key in pretoken_freq.keys():
    for i in range(len(key)-1):
        pair_freq[key[i],key[i+1]] += pretoken_freq[key]

更新一个片段时，代码从旧序列的每个相邻对中减去 count，再向新序列的每个相邻对加入 count。例如，aba × 3 要减去 ab:3 和 ba:3，再加上 a+ba:3。没有变化的片段不需要更新计数，但源码仍会扫描所有片段，所以增量计数并不等于只访问受影响片段。

代码仅在 len(new_seq) != len(seq) 时处理计数变化，因为一次成功替换必然缩短序列。末尾的 if v > 0 会清除零票，防止后续继续合并已经不存在的对。如果出现负数，你仍要排查计数错误，不能把过滤结果当作更新正确的证据。

vocab[len(vocab)] = best_pair[0]+best_pair[1] 用当前条目数作为新 ID，而循环上界由 max_vocab_id 管理。二者初始均为 256，只要特殊词元插入时不跳号，就会保持相等。如果以后预留 ID 或删除条目，前一种写法就可能覆盖旧项。因此，扩展实现时应分别管理条目总数和下一个可用 ID。

vocab_size 指的是包含特殊词元在内的词表总数。特殊词元是为文本边界等用途单独保留的标记，也要占用词表位置。在 259−256 = 3 个位置中，如果特殊词元占了 ID 256，就只剩 2 次合并：257 为 ba，258 为 aba。没有特殊词元时才剩 3 次合并，但当前代码须先修复空分隔表达式，才能按这个预算正常训练。

pretoken_freq[tuple(new_seq)] = pretoken_freq.pop(seq) 会覆盖已有键，而不是把两边的次数加起来。如果目标已有 2 票、移入片段带来 3 票，赋值后就只剩 3，正确结果应为 5。统一从字节重放规则时，同一字节串的表示一致，本例没有触发冲突；扩展到已有片段状态时，这种写法却可能丢计数。下面的修改先弹出旧计数，再把它累加到目标键。

# train_bpe.py · train_bpe：建议替换原赋值
old_count = pretoken_freq.pop(seq)
pretoken_freq[tuple(new_seq)] += old_count

如果允许任意已有片段状态，单纯把赋值改成累加还不够。遍历旧键的快照时，某个键可能已经接收了迁入计数，随后又被当作原来的片段处理一次。你可以把这一轮的结果累计到新字典，让旧状态只负责提供输入，避免重复处理汇入键。

原注释（train_bpe.py · train_bpe）系统化了什么
“defaultdict用于统计频率，它不用检查键是否存在”缺失从 0 开始；元组构造、哈希有成本。
“统计所有token对的频率（不含预分词的边界…”按次数加权，不跨片段。
“增量更新，核心代码”旧对扣除、新对加入；仍全量扫描片段。
“更新pair_seq，注意操作是在预分词的单元中进行的”先减后加，迁移键时保留次数。
“注意，这里pair_freq是可能出现0值的”删零值，防止选择不存在的相邻对。

编码：按训练顺序重放合并 ​

编码器必须按训练时确定的优先级，把新文本转换成词元序列。训练已经决定了哪些合并先发生，编码阶段的任务是重放这些选择。如果编码器根据当前输入重新统计频数，就会改变合并优先级，使同一套词表对应不一致的切分规则。

训练与编码还必须共享同一套边界规则，否则重放相同的合并优先级也不够。前面发现的数字分支缺陷就是反例：训练统计中漏掉了数字，编码端却仍然识别数字片段。BPE 训练器没有见过这些数字的相邻对，自然也学不到对应的合并方式，编码时它们便只能落回基础字节词元。这使学习合并规则时所见的训练分布，与推理时实际输入的分布不一致；共享正则的目的，是让两端对同一文本划出相同的候选片段，而不只是把代码改成一行。

tokenizer.py · Tokenizer.encode 先把片段拆成 list[bytes]，也就是由单字节对象组成的列表。它随后调用 apply_merge 执行合并，再通过 bytes_to_token 将结果映射到 ID。规则编号（rank）表示合并优先级，数值越小越优先，但它不等于任意词表中的 ID。

tokenizer.py · apply_merge：控制流
def apply_merge(token_bytes, merges):
    while True:
        for merge in merges:
            (A, B) = merge
            for i in range(len(token_bytes)-1):
                if token_bytes[i] == A and token_bytes[i+1] == B:
                    token_bytes = token_bytes[:i]+[A+B]+token_bytes[i+2:]
                    break
            else:
                continue
            break
        else:
            break
    return token_bytes

for merge 每轮都从第一条规则重新扫描，for i 则从左向右寻找这条规则的第一处匹配。匹配后的第一个 break 退出位置循环；如果没有匹配，内层的 else: continue 就让程序尝试下一条规则。如果找到匹配，程序会跳过内层 else，再由第二个 break 退出规则循环，回到 while。只有全部规则都失败时，程序才执行外层的 else: break，结束合并。

切片表达式保留 i 左侧和 i+2 起的右侧，再用 [A+B] 替换中间两项。规则 [(b,a),(a,ba)] 编码 ababa 时，逐步结果为 [a,ba,b,a] → [a,ba,ba] → [aba,ba]。你可以看到，第二步仍然优先执行第一条规则，而不是顺势先合并左侧的 (a,ba)。没有特殊词元时，结果 ID 为 [257,256]；本页已有实跑包含特殊词元，所以结果为 [258,257]。

设片段长度为 n、规则数为 M，合并至多发生 n−1 次，因为每次都会减少一个符号。每轮扫描的比较量为 O(Mn)，因此总计为 O(Mn²)。切片复制还会带来 O(n²) 的工作，字节操作的成本需要另计。

tokenizer.py · Tokenizer.__init__ 创建了 merges_reverse[pair] = i，但后续没有使用它，因此它是未参与执行的死代码。这个映射本来可以用来查询 rank，并不是注释所说的“从后往前匹配”。一种改法是建立 pair → (rank,new_id) 字典，查询当前相邻对，选出最低 rank，再更新合并位置的邻居。tiktoken 的 src/lib.rs · _byte_pair_merge 以拼接字节查询 rank，其训练约定让 rank 兼作 ID。字典查询可以消除遍历规则带来的 M 因子，局部更新与堆则进一步减少搜索工作。

特殊情况与流式编码 ​

特殊标记的识别方式和流式输入的分块位置都会影响合并边界。特殊标记需要作为整体识别，不能进入普通字节片段的合并过程。流式编码则是逐块接收输入的方式，如果分块截断了一个可合并片段，即使最终字节没有丢失，词元序列也可能改变。

tokenizer.py · Tokenizer.encode 用 sorted(self.special_tokens, key=len, reverse=True) 让长标记优先匹配，防止短前缀抢先占用输入。代码随后转义标记中的正则字符，再把这些标记拼成分隔表达式。regex.split(f'({delimiter})', text) 中的括号会保留匹配到的标记，使编码器能够为它查找对应 ID。

chunk in special_token_reverse 比较的是完整字符串，因此不会把普通片段中的子串误判成标记。不过，special_tokens=[''] 是一个反例，因为切分产生的空片段也会被识别为特殊标记。空标记 ID 为 256 时，已有实测中 encode('a') 得到 [256,256,97,256,256]。实现应拒绝空标记，并用集合查询完整标记，避免把无内容的匹配当作正常输入。

train_bpe.py · train_bpe 的 re.split('|'.join(re.escape(x) for x in special_tokens), text) 在列表为空时会得到空正则，从而在字符之间切分。已有实跑使用 aba!aba!aba!aca、上限 258 和标记 []，结果是 merges == []，因为字母已经被隔开，训练器数不到相邻对。下面的修改在没有特殊标记时直接保留整段文本，有标记时才构造分隔表达式。

# train_bpe.py · train_bpe：建议的边界处理
if special_tokens:
    delimiter = "|".join(re.escape(x) for x in
                         sorted(special_tokens, key=len, reverse=True))
    chunks = re.split(delimiter, text)
else:
    chunks = [text]

训练时，特殊标记已经先加入词表，因此正文里再次遇到标记时，会把标记本身从普通训练片段中丢弃。丢弃标记不意味着可以把两侧拼回同一个片段，否则合并就会越过原来的边界。训练端也按长度从长到短匹配，是为了与编码端识别出相同的标记范围，让两端切出来的边界一致。

tokenizer.py · Tokenizer.encode_iterable 仅逐块执行 yield from self.encode(file)，不会缓存上一块的尾部。本页规则把 ba 编为 [257]，但把输入拆成 ['b','a'] 后，结果却是 [98,97]。两者都能往返还原原文，后者却漏掉了一次合并。因此，分块必须保持预分词和标记识别的结果，按换行分块也需要验证。每块仍然会生成完整的 ID 列表，所以内存用量随最大块增长。

解码与往返 ​

解码器需要先拼接所有词元的字节，再把结果解释成完整文本。单个词元未必构成合法的 UTF-8 字符，因为词元边界可能落在字符的字节内部。如果你逐个解码再拼接字符串，原本能组成完整字符的字节就可能提前变成替换字符。

tokenizer.py · Tokenizer.decode 先查词表累积字节，再执行 result_bytes.decode('utf-8', errors='replace')。基础 ID [228,189,160] 对应 E4 BD A0，把这些字节整体解码就能得到“你”。如果逐个解码，每个不完整的字节序列都会变为替换字符，所以拼接必须发生在解释 UTF-8 之前。

errors='replace' 只在拼接结果非法时触发，例如输入 [228] 会得到 �（U+FFFD）。这个选项处理的是字节如何转换成文本，并不负责修复词表查询。遇到未知 ID 时，前面的查表操作仍然会抛出 KeyError。

decode(encode(s)) == s 表示编码后再解码能够还原原文，这就是这里检查的往返性质。它要求 s 可编码为 UTF-8、预分词不漏字符、词表与规则一致，而且 ID 序列保持完整。特殊标记也会原样还原，因为它们在词表中有对应字节。外部提供的 ID 序列则可能包含非法字节，此时替换字符会造成信息损失。

怎么验：顺序与往返 ​

验证分词器时，需要分别检查字节往返、合并规则和精确编号。能往返只能说明字节没有被弄丢，不能说明合并规则选得正确，也不能说明 ID 编得准确。你需要把合并表与参考规则逐项比较，并另用已知输入核对输出 ID，才能把这两类错误查出来。

test_train_bpe.py · test_train_bpe 用 assert merges == reference_merges 检查规则内容及顺序，但对词表仅检查键集合和值集合，并不检查逐项映射。test_train_bpe_special_tokens 排除标记本身后，断言普通词元不含 b'<|'，再通过快照检查词表与规则。这里的快照是保存下来供比较的参考结果，而“not in vocab”注释并不是说特殊标记不应进入词表。

test_tokenizer.py 检查空串、ASCII、Unicode、文件往返及 tiktoken ID，其中 ASCII 是基本拉丁字符等组成的字符集，Unicode 则覆盖更广的文字范围。test_ascii_string_matches_tiktoken 已注释掉 ID 断言，但仍然检查词元列表。test_overlapping_special_tokens 检查长短标记各出现一次的情况，连续标记和尾随换行还需另测。两个 test_encode_iterable_tinystories_* 检查往返与参考 ID，并另测 Linux 内存，但这些测试不能保证任意分块都安全。

小结 ​

这份实现需要在训练、编码和解码之间保持同一套分词约定。训练器划定片段边界、统计相邻对，再按频数和并列规则生成合并表。编码器复用边界和优先级，把字节转换成 ID，而不会重新学习频数。解码器查回字节并整体解释 UTF-8，因此往返、规则顺序和精确 ID 需要分别验证。当前的瓶颈仍是训练时每轮全量扫描片段，以及编码时每次从第一条规则重新扫描；增量计数并未消除这两部分工作。
