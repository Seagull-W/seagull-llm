# 解读董彬团队的形式化数学工作线：检索、形式化与证明搜索怎样接起来

本文解读北京大学董彬（Bin Dong）及合作者在 2024 年 3 月至 2026 年 11 月公开的形式化数学工作，以 **LeanSearch v1/v2、Aria、Reap** 为主干，用 Matlas、Chain of States 和 FATE 解释它们的输入、接口与评测边界；AI4Math review 只用于定位这条工作线。数字分别对应文末列出的论文版本。

**这条工作线最鲜明的重心，在检索与形式化之间的知识组织：把数学中的依赖变成可以调用、检查和修正的对象。** LeanSearch 要找到能共同支撑证明的一组库引理；Aria 要找准定义，并补出库里没有的概念。Reap 将这条线延伸到已形式化目标上的证明搜索，让策略模型的每个动作落到真实 Lean 状态上，再用搜索轨迹训练模型。贯穿它们的是三种不同的依赖：证明对引理的依赖、陈述对概念定义的依赖、子目标对后续证明步骤的依赖。

这一区分直接影响工程顺序。若形式陈述已经把原问题译错，后面的搜索仍可能得到一个完全合法的 Lean 证明；若陈述正确但前提缺失，搜索又可能耗在重新推导库中已有结果上。因此，搭建这类流水线时，先确认目标陈述和库接口，再增加搜索预算，比只盯着最终证明成功率更有诊断价值。这个判断来自 Aria 的编译／语义落差，以及 LeanSearch v2、Reap 固定其他组件后替换检索器的实验。[Aria §3–4](https://arxiv.org/pdf/2510.04520v1#page=3)，[LeanSearch v2 §4.3](https://arxiv.org/pdf/2605.13137v2#page=9)，[Reap §4.4](https://arxiv.org/pdf/2611.02678v1#page=8)

## LeanSearch：从找到一条声明，到找齐一条证明路线

Lean 是检查形式化证明的语言与证明助手，Mathlib 是它的数学库。证明状态记录当前假设和待证目标，tactic 是改变这个状态的 Lean 程序。模型需要能被代码调用的库声明，包含准确名称、参数和类型。LeanSearch v1 解决的入口问题很具体：数学家输入熟悉的定理名字或自然语言描述，库里的名字却未必相同。论文以柯西中值定理为例，对应声明名是 `exists_ratio_deriv_eq_ratio_slope`，直接搜索常用数学名称未必命中。[LeanSearch v1 §1](https://arxiv.org/pdf/2403.13310v2#page=1)

v1 把正式声明、文档字符串和相关定义交给 LLM，生成自然语言名称与描述，再把形式／非形式文本配对建索引；查询端也可扩写成相同的双语结构。它的基准包含 **50 条查询、18 组搜索意图**，查询形式覆盖自然语言、LaTeX、定理名称与 Lean 表达式。评测关心的是返回声明是否匹配目标或有助于找到目标，尚未要求一组结果能拼成完整证明。[LeanSearch v1 §3–4，表 1–2](https://arxiv.org/pdf/2403.13310v2#page=3)

### 标准模式：把声明的含义补全，再做排序

LeanSearch v2 的标准模式仍然接收自然语言查询，但语料准备更依赖库的结构。Jixia 静态分析器抽取 Mathlib 声明及引用关系；系统按依赖图的拓扑顺序，自底向上生成自然语言描述，使上层声明的解释能够引用已经解释过的下层定义。索引覆盖 Mathlib **v4.28.0-rc1** 中可抽取的定理、定义、类型类、实例等声明。对定义等对象，编码内容包含定义体；对定理则不把证明项当作同一种语义信息处理。[LeanSearch v2 §3.1](https://arxiv.org/pdf/2605.13137v2#page=4)

检索使用 Qwen3-Embedding-8B，先取 50 个候选，再用 Qwen3-Reranker-8B 重排。两个模型都没有针对 Mathlib 做专项微调；数学知识通过依赖感知的语料和按声明种类设计的提示进入系统。因此，“不做领域微调”仍包含了专门的语料工程。[LeanSearch v2 §3.1](https://arxiv.org/pdf/2605.13137v2#page=5)

这里的 **nDCG@10 为 0.623，LeanFinder 为 0.533**，测的是单条目标声明在前十名中的位置与命中情况。主表实际使用 MathlibQR 的 **810 条查询、171 个目标声明**，它们的目标声明在各系统的 Mathlib 快照中都存在；完整 MathlibQR 则有 946 条查询、200 个声明。去掉重排后，v2 的 nDCG@10 为 0.494。这个对照支持“重排是当前增益的重要来源”，却不能单独把全部增益归给依赖图。[LeanSearch v2 §4.1，表 1](https://arxiv.org/pdf/2605.13137v2#page=7)

### 推理模式：检索失败会改变证明草图

全局前提检索处理的是另一件事。论文中的例子是证明素数 $p$ 对应的多项式 $(x^p-1)/(x-1)$ 在整数系数下不可约。直接沿题目词面搜索，很难想到“分圆多项式”。若先认出这条路线，就能分别寻找几何级数恒等式、素数阶分圆多项式的表达式、分圆多项式的不可约性，利用散落在不同模块中的引理完成证明。这里需要恢复的是**一条路线所需的前提集合**。[LeanSearch v2 §1，图 1](https://arxiv.org/pdf/2605.13137v2#page=2)

推理模式先写证明草图，为每一步生成查询，再调用标准模式。过滤器可以明确返回空集；判别器检查整条草图能否被这些结果支撑，失败时指出缺失前提或类型约束问题，要求改写路线。初始草图之后最多再修订三轮。允许“这一段没有找到可用结果”很关键：强行保留 top-k 总能给出一些名字，却会掩盖计划根本不受库支持的情况。[LeanSearch v2 §3.2](https://arxiv.org/pdf/2605.13137v2#page=5)

MathlibMPR 从已合并的 Mathlib PR 中选取 **69 条定理**。每条定理有 1–8 个真值前提组，组内引理在对应步骤上可以替代；部分定理还标注了替代证明路线。两个指标分别回答“找到了多少需要的组”和“有没有找齐一条路线”：

| 系统与输入 | 前提组 Recall@10 | 完整路线 Covered@10 |
| --- | ---: | ---: |
| LeanSearch v2 推理模式；非形式描述＋形式陈述 | 46.1% | 30.4% |
| DIVER 完整流水线；相同类型输入 | 38.0% | 24.6% |
| DIVER 的 retriever＋GroupRank 变体 | 38.5% | 24.6% |
| LeanStateSearch；形式证明状态 | 9.3% | 2.9% |

来源：[LeanSearch v2 §4.2，表 2](https://arxiv.org/pdf/2605.13137v2#page=8)。Recall 先计算每条定理命中的前提组比例，再对定理做宏平均；组内任一可替代引理命中即可。Covered 则要求原路线或某条已标注替代路线的全部前提组都被命中。**46.1% 不是已证明的定理比例**；连候选集合已经找齐一条路线的比例也只有 30.4%。此外，表中 DIVER 的一个变体达到 38.5%，所以摘要中的 38.0% 应理解为完整 DIVER 流水线，而非所有变体中的最高值。

9.3% 也不能解释为逐步前提选择全面失效。LeanStateSearch 接收当前证明状态，服务于下一步 tactic；全局检索接收整条定理及描述，试图覆盖整条路线。这个对照揭示任务范围不匹配。Reap 后面仍然采用逐状态前提选择，正是因为它需要另一种接口。

### 下游的 20% 增益落在哪里

LeanSearch v2 另做了固定 prover loop 的实验：证明与反思模型均为 Claude Sonnet 4.5，最多八轮反思，以通过 Lean 检查且没有有效 `sorry` 占位的证明计成功。结果是：

| 接入的检索配置 | FATE-H，100 题 | MathlibMPR-Prop，50 题 |
| --- | ---: | ---: |
| 无检索 | 4/100（4%） | 2/50（4%） |
| INF-X-Retriever | 16/100（16%） | 5/50（10%） |
| LeanSearch v2 标准模式 | 14/100（14%） | 5/50（10%） |
| LeanSearch v2 推理模式 | 20/100（20%） | 7/50（14%） |

来源：[LeanSearch v2 表 3、附录 B.4](https://arxiv.org/pdf/2605.13137v2#page=9)。MathlibMPR-Prop 是可统一写成 tactic 证明占位形式的 50 题子集。**20%、16%、4% 都来自 FATE-H 上这一个受控框架**，没有采用 miniF2F 的 pass@32 口径。

“只换检索器”的实际集成也有边界：标准模式只在编译失败后的反思阶段触发；推理模式在首轮提供草图和前提集合，后续反思退回标准模式检索，不会每轮重新规划全局路线。因此，这里比较的是固定证明模型和反思轮数下的检索配置，包括查询方式、触发时机和草图信息；不是等 API 调用量的纯向量排序实验。[LeanSearch v2 附录 B.4，表 7](https://arxiv.org/pdf/2605.13137v2#page=20)

### Matlas 把检索扩展到论文，但返回对象变了

Matlas 将相似的依赖展开思路用于数学文献：从 **43.5 万篇论文与约 1,900 本教材**抽取 **807 万条数学陈述**。论文语料来自按 ICM 引用准则筛出的 180 本期刊，覆盖 1826–2025 年。系统先定位陈述，再抽取局部依赖，构建每份文档内部的依赖图，逐层展开定义与上下文，然后建立语义索引。[Matlas §3.1–3.3](https://arxiv.org/pdf/2604.17484v1#page=3)

它补充的是“数学文献中有什么可用结果”。LeanSearch 返回可在 Mathlib 中调用的声明，Matlas 返回经过 OCR、抽取和展开的非形式陈述；后者进入 Lean 证明前还需要匹配已有形式版本，或补定义、补证明。807 万是语料规模，不能作为已核验引理数量或证明增益。图中的 Matlas 到形式化模块因而是一条待完成的接口，不是这几篇共同报告的端到端系统。

## Aria：最容易被高估的是“陈述已经编译通过”

Aria 处理**定理陈述的自动形式化**。它首先需要把“这道题究竟在说什么”写对，证明正文可以仍是 `sorry`。这与 prover 去掉 `sorry`、构造完整证明是两项任务。一个类型正确但概念选错的陈述可以通过编译，Lean 也不会替人判断它是否忠实于原来的自然语言问题。[Aria §1、§3](https://arxiv.org/pdf/2510.04520v1#page=1)

Aria 的 Graph-of-Thought 是概念依赖图。系统自顶向下拆解目标，用 LeanSearch 为每个概念找规范定义；如果找不到，就继续拆成前置概念。叶节点能落到 Mathlib 后，系统自底向上生成缺失定义，再生成最终陈述，每个节点都可利用编译错误反复修正。论文以 Cohen–Macaulay 模为例说明为何必须补定义：仅检索几个相似名字，无法代替构造目标概念所需的层层依赖。[Aria §3.1，图 1](https://arxiv.org/pdf/2510.04520v1#page=4)

AriaScorer 检查另一层问题。它将原陈述分解成假设与结论，用 Jixia 提取生成代码实际引用的 Lean 术语，再查回这些术语的类型、定义体与自然语言解释，交给 LLM 逐项判别。一个具体错误是把八阶四元数群写成 `QuaternionGroup 1`：论文所用定义下，这对应四阶循环群，八阶四元数群应为 `QuaternionGroup 2`。表面名字非常接近，查定义才能识别参数含义。[Aria §3.2、附录 B.3](https://arxiv.org/pdf/2510.04520v1#page=6)

| 任务 | Aria 编译成功率 | Aria 最终正确率 | 对照与判定条件 |
| --- | ---: | ---: | --- |
| ProofNet 陈述形式化 | 91.6% | 68.5% | 最终指标还需通过 AriaScorer |
| FATE-X 陈述形式化 | 69.0% | 44.0% | 最佳基线 Goedel-V2 在 pass@128 下为 24.0% |
| 14 条交换代数同调猜想的陈述形式化 | 未单列 | 6/14（42.9%） | 结果人工核验；表中其他模型均为 0 |

来源：[Aria §4.1–4.3，表 1](https://arxiv.org/pdf/2510.04520v1#page=7)。常规实验的语义判定阈值为 **α=0.9**。Aria 在 FATE-X 上平均调用模型 **17.7 次／题**，每个生成节点的反思循环允许 16 次修正；因此其系统结果不能标作单次 LLM 生成的 pass@1，也不能把平均调用数当成与 Goedel-V2 等 token、等费用的预算。[§4.2、§4.3.2、附录 C.1](https://arxiv.org/pdf/2510.04520v1#page=7)

91.6% 与 68.5% 的落差说明，编译检查遗漏了大量语义问题；而“最终正确率”仍含语义判别器的误差。在 FATE-X 的 69 条可编译输出上，两名专家构建的标签用来检验 AriaScorer。α=0.9 时，它给出 42 个真阳性、15 个真阴性、2 个假阳性和 10 个假阴性。这个判别器减少了误收，却仍会误放和误拒；表中的 44% 是其判定口径，不能直接改写成“44 道题都经专家确认正确”。[Aria §4.3，表 2](https://arxiv.org/pdf/2510.04520v1#page=8)

消融进一步说明，不同任务不能收成同一条进步曲线：

| Aria 配置 | FATE-X 最终正确率 | 同调猜想最终正确率 |
| --- | ---: | ---: |
| 完整系统 | 44.0% | 42.9%（6/14） |
| 去掉编译反馈反思 | 14.0% | 0 |
| 去掉递归 GoT 分解 | 38.0% | 7.1%（1/14） |
| 去掉在线检索 RAG | 43.0% | 0 |

来源：[Aria 附录 C，表 3–4](https://arxiv.org/pdf/2510.04520v1#page=23)。FATE-X 上，反思的消融损失最大，去掉 RAG 的最终指标只降一个百分点；到了 14 条猜想，去掉 RAG 则没有成功样本，去掉递归分解也只剩一条。较复杂概念更依赖检索与定义合成，是这些结果支持的解释；“加入检索总会大幅提升形式化”则过强。小样本的 42.9% 也只是六条陈述形式化成功，绝不是解决了六条猜想。

### 已有非形式证明时，Chain of States 补的是状态转换

Aria 给出目标陈述后，证明仍可能卡在“自然语言的一步，在 Lean 里究竟要改变什么”。Chain of States 将非形式证明先译成一串中间证明状态，再为相邻状态生成 tactic。系统先尝试常见自动化 tactic，再用 DeepSeek-R1 生成局部转换；若执行后的状态与预期不符，利用错误反馈重写，必要时放弃那个中间目标，直接尝试完成剩余证明。[Chain of States §4–5](https://arxiv.org/pdf/2512.10317v2#page=12)

它说明“陈述正确”与“完整证明成功”之间还有可显式建模的接口。其 miniF2F-test 的 **69.2%** 使用因兼容性保留下来的 **227 题**，且输入已有非形式证明，部分证明经过人工修正；表中预算上界写作 **20×15×32 次 DeepSeek-R1 调用／题**。这不能与 Reap 在完整 244 题上的 pass@32 直接排名。[Chain of States §6.1.2、§6.3，表 3](https://arxiv.org/pdf/2512.10317v2#page=21)

## Reap：训练改变了证明组织，也改变了动作的计算颗粒度

Reap 把策略—价值引导的蒙特卡洛树搜索直接实现在 Lean 内部。模型提出 tactic，Lean 执行并返回新状态；可替代的 tactic 构成 OR 分支，必须全部完成的独立子目标构成 AND 分支。子目标若仍共享未解决的元变量，就保留耦合状态，不贸然拆开。价值头估计剩余证明搜索成本，与策略先验共同指导搜索。[Reap §3.1](https://arxiv.org/pdf/2611.02678v1#page=3)

这个实现选择让训练 rollout 与推理共用状态转移、搜索和验证逻辑。搜索树把根节点标为完成后，系统还会恢复原始状态、重放所选 tactic，再走 Lean 的声明检查流程：动作可能引入辅助声明或推迟证明义务，树内的“完成”不能替代最终验证。对熟悉 agent 系统的读者，这里的关键是环境反馈和训练轨迹来自同一套执行语义。[Reap §3.1](https://arxiv.org/pdf/2611.02678v1#page=5)

Reaper-1 的策略—价值主干是 **Qwen3-1.7B-Base**，经过 Lean／数学语料的继续预训练、状态—前提—tactic 的监督学习，再做搜索驱动的强化学习。这里的 RL 采用 expert iteration：搜索产生通过重放验证的成功轨迹，用其动作训练策略，并用 AND–OR 树回传的成本训练价值头。五阶段 RL 使用约 **2.5 万道 AoPS 训练问题**；RL5 每题最多 8,192 次模拟、pass@8，进一步筛选成功轨迹。不能把这 2.5 万题当成全部预训练和监督数据规模。[Reap §3.2、附录 A](https://arxiv.org/pdf/2611.02678v1#page=5)

它还依赖一个单独训练的 **PS-2 前提选择器**：基于 Qwen3-Embedding-8B，在 Mathlib v4.28.0-rc1 上以状态—前提配对数据训练，去重后有 897,414 对，其中 896,902 对用于训练。它在 prover 的 RL 中保持固定，每个状态返回八条声明。**“1.7B prover”描述的是生成与价值主干，并不涵盖默认系统的全部神经模型。** PS-2 沿用 LeanSearch-PS 的训练思路，与 LeanSearch v2 的无专项微调、全局路线检索是不同组件。[Reap §4.1、附录 B](https://arxiv.org/pdf/2611.02678v1#page=7)

### 79.9% 是带检索与搜索预算的系统结果

最终系统在 **244 道 miniF2F-test 上解决 195 道，即 79.9%**。pass@32 指每题最多 32 次独立搜索中至少成功一次；每次搜索上限为 **8,192 次 MCTS 模拟**，策略每次评估采样六个 tactic，生成长度上限 1,024 token、温度 0.99。论文报告这次完整评测使用 **32 张 A100 与 800 个 CPU 核，约三小时**。模型参数少，并不意味着这个成绩来自低预算单次生成。[Reap §4.1、表 1、附录 A 表 6](https://arxiv.org/pdf/2611.02678v1#page=6)

固定最终 RL5 模型和搜索配置，只替换前提选择器，结果发生变化：

| 前提选择器 | miniF2F-test，pass@32 |
| --- | ---: |
| PS-2，独立神经检索器 | 195/244（79.9%） |
| SineQuoNon，规则式选择器 | 185/244（75.8%） |
| MePo，规则式选择器 | 165/244（67.6%） |

来源：[Reap §4.4，表 3](https://arxiv.org/pdf/2611.02678v1#page=8)。SineQuoNon 的结果说明这个 prover 可以在不重训的情况下更换前提组件，但其默认 79.9% 仍应连同 PS-2 报告。搜索预算也有边际收益递减：同为 pass@32，每次 512 次模拟已解出 188/244，增加到 8,192 次为 195/244。[Reap §4.5，表 4](https://arxiv.org/pdf/2611.02678v1#page=8)

### 搜索步数减少，不等于每一步变便宜

Reap 最有解释价值的分析，是将 SFT、RL4、RL5 都能解决的 **151 题**固定下来，观察训练怎样改变搜索。每题取最早成功轮次的验证证明，同轮并列时取顶层动作较少的，作为代表证明：

| 同题比较的量 | SFT | RL5 |
| --- | ---: | ---: |
| 代表证明的平均顶层动作数 | 21.7 | 5.2 |
| 成功搜索树的平均节点数 | 2,368 | 119 |
| 代表证明中动作字符数中位数 | 19 | 66 |
| 代表证明中每动作的 tactic 标识符数 | 1.38 | 2.80 |

来源：[Reap §4.6、附录 C.1–C.3，表 5、8–9](https://arxiv.org/pdf/2611.02678v1#page=9)。与此同时，搜索级 tactic 执行日志中的评估延迟中位数从 **12.0 ms 升至 43.2 ms**；该统计覆盖三次运行的已完成执行记录，不限于 151 题的代表证明。[Reap 附录 C.4，表 10](https://arxiv.org/pdf/2611.02678v1#page=17)

后期策略更常用中间断言、组合 tactic 和嵌套证明，把多个内部操作包装成一个外部动作。单位 tactic 动作计费的价值目标因此同时奖励了有用的证明组织，也可能奖励把计算藏进更大的动作。实验支持“顶层搜索交互被压缩”；是否降低总成本，还要同时看模型调用、生成 token 和 Lean 执行时间。作者也据此提出，把执行时间或动作复杂度纳入未来成本目标。[Reap §4.6–5](https://arxiv.org/pdf/2611.02678v1#page=9)

## FATE 留下的分歧：更会写 Lean，不保证更会修正数学推理

FATE 将困难推进到抽象代数与交换代数。v4 的 FATE-M 有 150 题，FATE-H 与 FATE-X 各 100 题；FATE-X 中 **38% 的题需要 Mathlib 原先没有的定义**，这些定义已经写入题目文件。这里的 prover 需要使用给定定义完成证明，而 Aria 的陈述形式化任务还要把概念译对，两者即使使用同名数据集，也不在做同一项工作。[FATE §3](https://arxiv.org/pdf/2511.02872v4#page=4)

FATE v4 的 whole-proof 基线在每题 **64 次独立尝试、单次最多 64k token** 下，FATE-H 最好为 **3/100**，FATE-X 全部为 **0/100**。这些是当时表列模型及生成方式的结果，与 LeanSearch v2 后来的 Claude Sonnet 4.5＋检索＋八轮反思实验协议不同，不能把 3%→20% 归为检索的净增益。[FATE §4.1–4.2，表 1](https://arxiv.org/pdf/2511.02872v4#page=6)

分阶段分析揭示了更尖锐的差异。FATE-H 上，专家判定 DeepSeek-R1 的自然语言证明 pass@1 正确率为 **71%**，DeepSeek-Prover-V2 为 **39%**；最终形式证明 pass@64 却分别为 **0% 和 3%**。在自然语言正确、形式证明失败的样本中，Mathlib 幻觉分别出现在 70/71 与 35/39 条尝试，Lean 熟练度错误出现在 70/71 与 36/39 条；这些错误类型可以重叠。形式化仍是突出障碍，但专门优化形式证明，也没有自动保住前端数学推理能力。[FATE §4.3–4.4，表 2–3](https://arxiv.org/pdf/2511.02872v4#page=7)

论文对同源模型推理过程的定性比较还发现：DeepSeek-Prover-V2 的某些“反思”只是重启论述或改变措辞，未定位和修复逻辑缺口；DeepSeek-R1 更常完成有效修正。这是特定模型、样本与错误分析中的观察，尚不能归纳为专项训练必然损害反思。它与 Reap 的 RL 增益并不冲突：前者考察自然语言推理如何纠错，后者优化真实 Lean 状态上的搜索行为。接入流水线时，两段都需要各自的评测。[FATE §4.5](https://arxiv.org/pdf/2511.02872v4#page=9)

## 自己搭流水线：先固定目标与接口，再增加搜索

依据这些实验，工程起点应随输入而变：已有形式陈述时，优先建立可重放的 Lean 执行环境和前提检索；从自然语言问题出发时，先增加 Aria 式的定义检索、缺失概念合成与语义检查。具体可以按以下顺序推进，这是本文的工程判断：

1. **把声明标识与类型当作检索结果的一部分保存。** 固定 Lean／Mathlib 快照，返回全限定名、类型、定义内容与依赖信息。LeanSearch v2 的跨快照公平子集，以及 Aria 的参数误读案例，都表明仅存一段相似文本不足以支撑调用。
2. **把“译对题目”单列为验收点。** 同时保留编译结果和语义判定，抽查新增定义及判别器接受的结果。Aria 的 91.6% 编译率与 68.5% 最终指标之间的空隙，是最容易被一个绿色编译状态掩盖的失败。
3. **按任务选检索颗粒度。** 查已知概念用声明搜索；不知道整条证明要借助哪些工具时，用草图驱动的全局检索；逐步搜索则让前提选择跟随当前状态。LeanSearch v2 和 Reap 给出了后两者各自的正面证据，无需强行统一成一个查询接口。
4. **固定检索配置后，才比较搜索与 RL。** 同时报成功数、尝试次数、每次模拟预算和执行成本。Reap 的规则检索替换实验能分离组件贡献，151 题配对分析能分离题目难度变化；仅报告“动作更少”会漏掉复合 tactic 的额外成本。

董彬与 Ju 的 AI4Math review 将这类工作放在通用数学建模中的推理、检索与 agent 工作流一侧，并将证明带来的理解和可复用工具视为比形式正确性更远的目标。对这里几项系统，一个具体的检验是：检索是否找到可复用的库引理，形式化是否忠实表达新概念，搜索是否产生可检查的中间结构。当前论文为这些局部接口提供了证据；把它们串起来后的研究级端到端成功率，仍需在共同任务和共同预算下测量。[AI4Math review §1、§4](https://arxiv.org/pdf/2601.13209v5#page=2)
