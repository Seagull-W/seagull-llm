## 文章的主线

作者把近期工业界智能体沙箱放在同一个判断下：产品很多，底层却都沿用 serverless，公开宣传集中在“更快地创建”；而智能体的时间大部分花在等待上，创建并不是瓶颈。训练场景里，DeepSeek DSec 处理了突发创建和镜像分发，其余性质仍待研究。作者由此提出三个系统问题：利用模型推理的等待时间、提高部署密度、重新管理有状态会话。

## 读这篇归纳需要的概念

智能体在这里指会自己决定下一步、并让外部环境去做的模型程序。一次循环通常是：模型读到目前为止的对话和工具结果，生成下一段输出；若输出里包含一次工具调用，执行环境就去跑命令、改文件或访问网络，再把结果送回模型。模型生成这段输出的时间，原文称为推理时间，短则数秒，长则数百秒。这段时间里，执行环境常常无事可做。后文说“大部分时间在等待”，指的就是这件事。

沙箱是套在这次执行外面的隔离边界。模型写出的命令不可全信，提示注入或模型犯错都可能删文件、扫网络、影响别人。沙箱的目标是：这个智能体只能动自己那份环境，出错或被利用时，不波及宿主机和其他用户。它不负责让模型答对，只负责把执行关在一个可丢弃的范围里。

隔离有几种常见强度，后文里的产品名就是在这些强度之间选择：

| 叫法 | 实际隔离的是什么 | 和后文的关系 |
| --- | --- | --- |
| 普通容器 | 进程看到的文件系统、网络和进程列表被分开，但大家仍用宿主机的内核。Docker 是最常见的打包和运行方式 | OpenSandbox 的默认后端 |
| gVisor | 在容器和宿主机内核之间加一层用户态内核，系统调用先被这层拦住 | Kubernetes 上用 RuntimeClass 换上去的更强隔离 |
| 微虚拟机 | 每个沙箱自带一个很小的内核，由 Firecracker、Cloud Hypervisor 这类精简虚拟机监视器跑起来。隔离接近虚拟机，启动比传统虚拟机短 | CubeSandbox 的 MicroVM；OpenSandbox 的 Fast Sandbox |
| Kata | 兼容普通容器接口，但每个容器实际跑在一台轻量虚拟机里 | 原文把它和 gVisor 并列为更强隔离的 RuntimeClass |

RuntimeClass 是 Kubernetes 用来选择“这个 Pod 由哪种运行时执行”的字段。不改业务描述，只把底层从普通容器换成 gVisor 或 Kata。Pod 是 Kubernetes 的调度单位，这里可以把它理解成“分到某台机器上的那一个沙箱进程组”。

serverless 是一种使用方式，不是一种隔离技术。用户不管理机器，平台按一次请求或一个会话创建执行环境，用完就收。它的经典难题叫冷启动：环境还没准备好，第一次请求要先等启动完成。传统虚拟机或没有预热的容器，这个等待常常是秒级。平台用两件事把它压短。一是预热池，事先启动一批空环境，请求来了直接取用，代价是空着也占内存。二是快照恢复：把一个已经启动好的环境的内存拍下来，新沙箱不重新开机、不重新跑初始化，而是从这张快照接着跑。AWS Lambda 的 SnapStart 就是后一种。微虚拟机本身也把启动压到了大约百毫秒这一量级，但那仍是“创建有多快”的优化。原文说各家“优化更快地创建”，指的就是继续压这个时间，并用博客宣传这个毫秒数。

快照能被许多沙箱共用，靠的是写时复制。内存上，多个沙箱映射同一份快照文件，谁改了某一页，只把那一页变成自己的副本。磁盘上，XFS reflink 做类似的事：看起来各有一份磁盘，实际先共享模板的数据块，写入时才分开。OCI 镜像是容器镜像的通用格式；原文里的模板由这种镜像做出来，冷启动一次，再把内存存成快照。所以“创建时并不真正启动虚拟机”的意思是：贵的那次启动已经提前做完，用户请求只做映射和克隆。

CubeSandbox 那条链路可以用 Kubernetes 里更常见的角色来记：

| 原文中的组件 | 在这次创建里做什么 | 作者给出的对照 |
| --- | --- | --- |
| CubeAPI | 对外接受创建请求，接口与 E2B 兼容 | API Server，集群的入口 |
| CubeMaster | 决定沙箱放上哪台机器 | 调度器 |
| Cubelet | 落在那台机器上的代理，负责真正把它拉起来 | kubelet |
| CubeShim | 实现 containerd 的 shim 接口，让上面的系统可以像管理容器一样管理这台微虚拟机 | 容器运行时 |
| MicroVM | Cloud Hypervisor 的一个分支，提供隔离 | 最终跑起来的环境 |

containerd 是节点上管理容器生命周期的程序。shim 是它为每个容器拉起的适配进程。CubeShim 实现这个接口，所以上层不必专门学会如何操作微虚拟机。

空闲超时后挂起，是把一个暂时没人用的沙箱冻住：CPU 不再跑它，内存状态保留，下次请求再恢复。这和“删掉再重建”不同，恢复时还带着上次的内存。原文的服务场景按用户会话保留沙箱，一个会话一份，而不是每个工具调用新建一份。后文的 per-session 就是这个粒度。

超卖是分配出去的 CPU 或内存超过机器实际拥有的量。智能体大部分时间在等模型，于是很多沙箱同时空闲，平台指望它们不会一起变忙。赌错了就会争抢 CPU，或者内存不够、触发 OOM，由系统杀掉进程。传统 serverless 常根据函数以往的用量来决定能超卖多少。原文认为这一步套不到智能体上，因为下一步调用哪个工具、那个工具有多重，都不好由历史平均值预测。

无状态和存算分离是云计算里的习惯：计算节点可以随时丢掉，真正要留的数据放在别的存储里。智能体沙箱相反。它改过的文件、装过的依赖、开着的后台进程，就是任务还没做完的现场。训练时这个矛盾更大。GPU 上的训练任务可能被抢走或要同步权重，这时成千上万个沙箱要同时暂停；这些现场放在本机还是别处、暂停时还占不占内存、恢复时能不能换一台机器，就是原文说的本地状态和远端状态。

镜像分发是另一个独立问题。沙箱要先在节点上有一份环境模板，通常是容器镜像。训练一步可能同时要很多份环境。若每份都临时从远处拉镜像，创建就会卡在下载上。TL;DR 说 DSec 解决了突发创建和镜像分发，只说明作者认为这两个问题在那份工作里有了做法。那一节正文未读到，这里不描述具体做法。

这些词够用来读后面的归纳。它们不证明某一家产品的毫秒数，也不代替未读到的实现细节。

## 为什么沙箱成本突然值得单写

作者的背景判断是：聊天机器人变成会调用工具、执行命令、读写文件的智能体之后，执行环境为了隔离被放进沙箱。过去模型推理很贵，沙箱成本被当成可以忽略，研究也多集中在安全。现在旗舰模型输出仍是每百万 token 数十美元，但 DeepSeek V4-Flash 这类平价模型只要旗舰价格的几十分之一，已经能驱动复杂任务。模型变便宜之后，沙箱在总成本里不再是零头。

文中给出两个数字，口径不同，不能合成一个“行业占比”：

- TrEnv-X 按 AWS Lambda 计费估算，部分智能体的执行环境成本可达总成本的 42%。检索到的参考文献片段没有包含 [1] 的完整题名，本文不补写这篇工作的方法。
- 作者实验室回放了 256 条编程智能体轨迹：codex 驱动 DeepSeek V4-Flash，任务来自 SWE-bench 与 Multi-SWE-bench。沙箱成本的中位数占总成本的 32%。

TL;DR 把这两类结果收成“三到四成”。这是作者的概括；42% 与 32% 分别对应上述两种估法。

## 先把两种用法分开

作者认为不能把所有“智能体沙箱”当成同一种系统。

服务场景是 Manus、Replit 这类产品的执行环境：集群里大量沙箱，供用户各自指挥模型完成任务。会话互相独立，各自到达、各自结束。E2B、Daytona、腾讯 CubeSandbox、阿里 OpenSandbox 被作者归到这一类。

训练场景用于后训练。模型在真实环境里做代码等任务，评分后再更新参数。它和服务场景的差别是：每个训练步骤成批拉起沙箱；同一道题常采样多条轨迹，这些沙箱从同一环境出发，行为也相似；调度还要和 GPU 集群一起考虑。公开资料少，多来自高校或校企合作，而且多还是预印本。

## 服务场景：看起来很热闹，结构很像

作者点名 Daytona、E2B、谷歌、AWS、腾讯、阿里都在做服务场景沙箱，并在博客或公众号里强调性能。已读片段里的判断是：仔细看实现，范式仍是传统 serverless，差别主要在通用优化。

腾讯 CubeSandbox 是这段里写得最具体的例子。请求链路是 CubeAPI → CubeMaster → Cubelet → CubeShim → MicroVM。CubeAPI 兼容 E2B；CubeMaster 集中调度；Cubelet 是节点代理；CubeShim 实现 containerd 的 shim；底层是 Cloud Hypervisor 的一个分支。作者把它对应到 Kubernetes 的 API Server、调度器、kubelet 和容器运行时。创建时并不真正启动虚拟机，而是从模板恢复：OCI 镜像冷启动一次后保存内存快照，新沙箱映射同一份快照，磁盘用 XFS reflink。作者认为这与 Firecracker 快照恢复、AWS Lambda SnapStart 同一思路。生命周期是一个用户会话一个沙箱，后台按空闲超时挂起，下次请求再恢复。

阿里 OpenSandbox 建在 Docker 和 Kubernetes 上。默认后端是 Docker；Kubernetes 上用 BatchSandbox 维持预先启动的 Pod 作为预热池，更强隔离则用 RuntimeClass 换成 gVisor 或 Kata。为绕开 Kubernetes 控制面延迟，另有 Fast Sandbox：在预先启动的 Pod 里跑 Firecracker，并从快照恢复。

已读片段在 Fast Sandbox 处截断。E2B、Daytona、谷歌 Agent Sandbox、AWS Bedrock AgentCore 在原文里被列入讨论和参考文献，但它们的机制段落不在这次取回的文本里，这里不转述。

## “错误的目标”指什么

“错误的目标”是作者的论点，不是某家厂商的自我表述。TL;DR 写的是：工业界花大量时间优化和宣传更快的创建，但创建不成为瓶颈，智能体大部分时间在等待。

文末的开放问题把这个判断说得更具体。智能体是模型推理和工具执行交替进行。等模型输出可以是数秒到数百秒。作者认为，serverless 里被抱怨多年的虚拟机冷启动，放在这个时间尺度上很快。因此继续把工程目标放在创建延迟上，没有打到时间主要花在哪里。

作者和合作者目前的观察是：模型推理期间把沙箱暂停或删掉，等下一次 tool call 再拉起，吞吐可以明显提高。文中引用 AgentSysBench：推理期间卸载沙箱，平均内存降到约原来的 1/4.6，端到端延迟增加不到 0.5%。本文没有读 AgentSysBench 原文，这个数字只作为添茶的引用保留。作者接着问：这段等待还能做什么；per-session 沙箱是不是合适的粒度；快照是否必须保留全部内存。

另外两个问题被作者称为同样普遍，并说 DSec 以及自己参与的工作和其他论文有类似观察：

- 部署密度。模型在推理、工具又各不相同，沙箱平均 CPU 和内存利用率很低，需要很高程度的超卖。传统 serverless 用历史数据预测函数资源，作者认为套不到这里：下一步动作难预测，不同动作的资源差也大。超卖和避免争抢、OOM，是还没定型的设计。
- 状态。云计算偏好无状态和存算分离，智能体沙箱却要一直留着文件修改、shell 环境和后台服务。训练时更极端：GPU 任务被抢占或同步权重时，大量沙箱同时暂停。状态放在哪里、暂停占多少资源、恢复能否换节点，作者认为都还没有好答案。

TL;DR 对 DSec 只下了一句结论：突发创建和镜像分发被解决了，更多性质仍要探索。训练场景那一节的正文没有出现在这次取回的片段里，所以本文不写 DSec 的架构、并发规模或安全机制，避免把其他文章里的 DSec 介绍算成添茶的话。
