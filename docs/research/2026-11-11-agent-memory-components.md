# Anthropic 的 agent 记忆：经验如何经整理进入下次会话

一个 agent 花了很久才弄清任务规则，换一次会话，却又得重新摸索。把历史留下来可以避免经历丢失，但后来的 agent 仍要从中找出有用的经验，判断哪些只是当时的猜测，再把可信的部分用到新任务中。Anthropic 的《The components of agent memory》讨论的正是这段过程：经验怎样从会话记录变成未来可以读取和依赖的知识。

这里的记忆特指从任务与交互中获得、跨会话保存的经验知识。权重更新改变模型参数，上下文学习发生在当前对话里，compaction 则用摘要替换旧轮次以继续任务；原文将它们与所讨论的跨会话记忆区分开。以下依据 Lance Martin 的[原文正文及图注](https://www.anthropic.com/research/components-of-agent-memory)，追踪一段经验如何被留下、挑选、校验、组织，最后进入下一次会话。

## 留下转写，才能在笔记之外回查经历

会话转写（transcript）保存先前发生过什么，为后来的检索和回看提供材料。Agent 可以直接搜索这些记录，也可以在任务进行时给显著事件打标记，或把观察写进跨会话保留的目录，形成记忆笔记（memory notes）。两者从这里开始分工：转写留下经历，笔记保存 agent 从经历中选出的内容和作出的判断。

这种分工决定了为什么保存笔记之后仍需要转写。笔记把一次探索压成一条规则，后续会话便可能省去重新探索的过程；但如果当时误解了观察，这条规则也会把错误带过去。保留可回查的经历，才能重新检查规则的来路，而不必只在几份互相引用的总结之间寻找依据。原文后面的月见山案例正是通过对照转写纠正笔记；其中的转写被当作核验记忆的 ground truth，具体作用是让 Claude 回看当时的经历。[原文 Memory notes 与 Dreaming can correct memory](https://www.anthropic.com/research/components-of-agent-memory)

不过，留下经历并没有替未来会话完成选择。随着记录增长，每次从头寻找、理解和提炼都会消耗计算；若要把这部分工作提前做掉，agent 就得在尚不知道未来问题的时候，判断哪些内容值得写成笔记。

## 选择笔记，是判断未来还需要什么

原文把显著性判断理解为一种对未来用途的预测：写下一条规则，是预期以后还会碰到类似情况；写下一个已验证事实，是预期后来的会话可以直接依赖它。这种判断既涉及信息是否重要，也涉及它是否容易重新获得。Pokémon Red 中的当前金钱和地图位置每轮都能从屏幕读取，另存一份容易冗余、过期；策略、计划和经过检验的规则却需要 Claude 自己探索，若不写下来，下一次便可能要重做这段探索。

Fable 5 据此组织了不同用途的笔记：顶层 `global.md` 保存当前目标、挑战道馆的预案和使用记忆的规则，`locations` 目录保存路线计划，`gameplay` 目录保存游戏策略。Opus 5.5 也用较小的笔记目录追踪当前目标和下一步行动，并随游戏进展重写。当前目标本身会变化，却仍值得保存，因为下一次行动需要靠它接续；判断的关键是未来用途和重新获取的难度。相比之下，Sonnet 3.7 大量保存逐次遭遇，随着游戏状态变化，又不断花时间整理过期内容，挤占了实际游戏行动。[原文 Claude has learned to judge salience](https://www.anthropic.com/research/components-of-agent-memory)

在任务进行时作出这些选择，可以趁相关细节仍在上下文中将其留下，并立即供后续轮次或会话使用，代价是写笔记会分走处理当前任务的注意力。更难的是，agent 当时未必知道观察意味着什么：失败可能提示了一条规则，也可能只引出几个尚未检验的解释。若这些解释以同样肯定的语气留在目录里，下一次读到它们时就容易把猜测当成知识。因此，选出值得记的内容之后，还要保住它的验证状态。

## 让猜测经过检验，让错误回到经历中纠正

CL-Bench 1.0 的数据库任务把验证与复用连了起来：Claude 连续回答需要查询数据库的问题，每次作答后得到正确解答，并有机会写记忆。实验运行在 Claude Managed Agents 上，每道题都从新会话开始；有记忆的条件允许检索跨会话保留的目录。这样，上一题的经验要影响下一题，就必须经过写入、读取和使用。下表是这个 database task 的 **mean reward**，对照为 stateless 基线与持久记忆目录。[原文图 3](https://www.anthropic.com/research/components-of-agent-memory)

| 模型 | Stateless 基线 | 有记忆目录 | 原文观察到的记忆行为 |
| --- | ---: | ---: | --- |
| Sonnet 4.6 | 0.330 | 0.364 | 为错误提出解释，但笔记散落着未经检验的猜测 |
| Opus 4.7 | 0.383 | 0.700 | 合并为参考文档，区分已检查与尚未确认的事实 |
| Sonnet 5 | 0.306 | 0.610 | 评分器检查后标记已确认答案，答错后写入纠正 |
| Opus 5 | 0.564 | 0.828 | 记录规则、规则成立的依据、既往答案及已发现的陷阱，形成闭环 |
| Opus 5.5 | 0.655 | 0.838 | 同样保存经过验证、可用于后续问题的规则 |
| Sonnet 5.5 | 0.644 | 0.833 | 同样形成验证与复用的闭环 |

这些笔记呈现出从猜测到可复用规则的差别。Sonnet 4.6 会解释自己为什么答错，却常常不检验解释，也不读取已有笔记；研究者提示它在回答前先读记忆，再明确测试假设后，同一任务的 mean reward 从 **0.364 提高到 0.641**。Sonnet 5 已能在没有额外提示时主动读取记忆。Opus 5 则把规则、规则成立的依据、既往答案与陷阱一起保存，后来的会话因而有了可以复用的判断依据。Opus 5.5 与 Sonnet 5.5 的无记忆基线更高，有记忆后的得分却与 Opus 5 接近。[原文图 3、图 5 左](https://www.anthropic.com/research/components-of-agent-memory)

这也解释了为什么“告诉模型记忆用来做什么”和“预先限定只能记什么”会产生不同效果。在同一任务中，研究者逐项测试内容限制，相对于不施加这类限制的记忆条件，“只记录失败”使记忆带来的 mean reward 增益发生负向变化：Opus 5 为 **−0.234**，Opus 4.7 为 **−0.150**，Sonnet 4.6 为 **−0.020**。失败能启动学习，但后续还需要成功的验证、已确认答案和规则成立的依据；只准记失败，可能把这些同样有用的内容排除出去。较强模型仅获知记忆目录可用，就能取得明显收益，而 Sonnet 4.6 需要的提示恰好补上了读取与检验这两个动作。提示是否有用，取决于模型在哪一步停住。[原文图 5 右及 Steering Claude to write memory](https://www.anthropic.com/research/components-of-agent-memory)

数据库任务每题都有正确解答，验证线索来得直接。在长程交互里，错误却可能一直没有被识别，甚至被后来几次会话反复强化。Anthropic 将利用交互间隙或后台计算回看记录、整理记忆的过程称为 **dreaming**；它承接原文介绍的 sleep-time compute 思路，让 Claude 有机会暂时离开当前任务，检查已经写下的判断。

Pokémon Red 的月见山案例说明了这种回看的必要性。山洞入口在地图西侧，出口在东侧，入口附近有一个跳下后无法直接返回的单向台阶。Claude 错把入口旁的宝可梦中心记在东侧，走出中心时便认为已经穿过月见山，随后跳下台阶，落回原来的路线。导航工具没有显示这次落差，它又把结果解释为“向西走过头”，于是保住了最初的错误判断。笔记中的方位既影响了行动，也影响了它如何解释行动结果。

研究者对含有这条错误笔记的目录执行 dreaming，让 Claude 对照会话转写检查位置判断。它发现错误、改写笔记后，重新进入山洞，最终抵达华蓝市。图 8 中，带 dreaming 的运行在累计第 **1,935 个动作**到达目标；未经修正的原始记忆条件与无记忆条件都没有抵达。未经修正的运行曾 **3 次**跌回同一条来路，之后转回山前的城市，结束时仍未完成目标。[原文图 6–8](https://www.anthropic.com/research/components-of-agent-memory)

把离开中心、跳下台阶和回到来路放在一起看，这段经历与“仍在西侧入口附近”相符，却与“已经穿山到东侧”的笔记冲突。转写让这种重新解释成为可能，而导航工具单次没有显示落差，并不足以支持“只是向西走过头”。原文报告了比对与改写的结果，但存档未给出完整动作轨迹、逐条工具返回或 dreaming 推理记录，因而无法定位是哪一条返回触发了纠错。

回看也有时效边界：历史经历可以帮助发现最初就写错的笔记，却不能单靠旧记录保证环境变化后的规则仍然成立。持续检查全部记忆又会增加读取和核验成本。原文提出，可以将 dreaming 集中在容易变化的信息上，或根据访问频率调整整理节奏；这些仍是待探索的安排。在线验证与离线回看共同维护笔记的可信度，但后台整理的结果可能来不及供当前任务使用。[原文结语](https://www.anthropic.com/research/components-of-agent-memory)

## 把可用经验组织成 wiki，同时保住来源和查找路径

即使每条笔记都可信，后来要用的内容也可能分散在许多文件中。Dreaming 因此还可以构建 **wiki**：Claude 围绕主题编写页面，将相关内容汇集起来，再用链接连接其他页面和笔记。后续整理继续添加、修改、去重并核对来源，使一次会话的工作成为下一次整理的起点。这里提前完成的是查找和组织工作，收益要看未来的问题是否需要这些连接。

Anthropic 在 Stainless 约 **35 万份内部文件、约 420M token** 的语料上建立了 **25 个问题**的评估集，让 Opus 5 agents 在连续 dreaming 会话中探索文件、维护链接页面，并通过共享日志协调。随着整理从 **2 轮、2M dreaming token** 增至 **128 轮、128M dreaming token**，这组问题上**判分标准的满足比例**如下：[原文图 10](https://www.anthropic.com/research/components-of-agent-memory)

| 回答问题时可用的资源 | 整理 2 轮后 | 整理 128 轮后 |
| --- | ---: | ---: |
| 仅 wiki | 13% | 48% |
| wiki 与搜索工具 | 54% | 61% |

同一评估中，仅搜索得分为 **53%**。经过更多整理，wiki 覆盖的内容更丰富，但单独作答仍低于搜索；两者合用才得到最高分。页面和链接可以让 Claude 从已组织的内容出发，搜索则保留了访问 wiki 尚未覆盖材料的途径。原文还报告，组合方式相对仅搜索**每个问题节省约 20,000 token**（未分列检索、阅读和推理各自节省多少）。这项节省发生在回答问题时，创建和维护 wiki 的 dreaming token 另计。预先组织材料能否节省总计算，还取决于后来使用多少次、少做多少重复查找，以及更新需要花费多少计算。

跨文档任务更能体现提前组织的用途。在一组并购材料的 **24 条判分项**中，多数需要整合多份文档，其中 **9 条**还需要判断或算术；针对需要跨文档整合、判断或计算的判分项，查询 wiki 得分 **87%**，仅搜索为 **73%**。而 Harvey LAB 的另一项法律简报任务有 **57 条判分项**，多数可以从单份文档直接检索，wiki 相对搜索没有显示出明确收益。当答案本来就能直接取出，提前把材料重新组织一遍，未必能改善作答。[原文图 11](https://www.anthropic.com/research/components-of-agent-memory)

组织过程还可能制造新的负担。图 12 的另一项 LAB 任务中，原始语料只有 **10 份文档、115 KB**，生成的 wiki 却达到 **203 KB**，为原材料的 **1.77 倍**。细节被大量重述，表示本身便成为更大的阅读对象。抽象多少又必须服从任务：若后续判分依赖合同原文，过度摘要会丢失关键内容，完整保留条款反而有必要。[原文图 12](https://www.anthropic.com/research/components-of-agent-memory)

一项模拟公司收购的 LAB 任务暴露了这类损失。初始指令只要求建立 wiki，没有交代合同条款对简报评分的重要性；多个 agent 同时写共享条款表，摘要不充分，又相互覆盖，导致依据 wiki 生成的简报只覆盖 **57 条事实中的 41 条，即 41/57、72%**。研究者让 Claude 反思失败、修改整理指令并重建 wiki，之后每份合同由单个 agent 编写独立页面，逐字引用条款。基于改进表示生成的简报覆盖 **57/57 条事实，达到 100%**。内容保留方式与协作写入结构在这里共同改变，结果反映的是这组修改的效果。[原文图 14](https://www.anthropic.com/research/components-of-agent-memory)

保存了条款，仍要保证从其他页面能走到它们。不同会话分别写页面时，可能先留下链接，却没有建立目标页；这种缺口会使已有内容难以被找到。图 15 的 LAB 任务中，第二轮 dreaming 找到 **9 条**指向不存在页面的链接，将它们改指描述同一文档的已有页面，并新增 **3 个页面**，其中包括索引。Wiki 的维护因此同时涉及内容和路径：既要保住任务所需的事实，也要修复会话之间留下的连接缺口。查来源、重建页面和修补链接都要持续花费计算，直接检索转写或原始材料仍然可以作为基础访问方式。[原文图 15 及结语](https://www.anthropic.com/research/components-of-agent-memory)

## 用少量注入内容，把下一次会话引向已有经验

一个已有内容、链接也完整的 wiki，仍可能在新会话中无人问津：Claude 必须先知道存在相关经验，才会去查。原文将 dreaming 的另一项作用称为 **promote notes up the memory hierarchy**，即挑出重要笔记，由运行框架在每次会话开始时预先加载到上下文。这样，agent 无需先想到搜索，就能看见关键内容或检索入口。[原文图 13](https://www.anthropic.com/research/components-of-agent-memory)

预先加载解决了入口问题，也把成本带到每次会话中。注入占用上下文 token，错误笔记可能因此被反复带入；即使加载成功，模型也未必执行其中的要求。原文援引 Claude Code 文档指出，更长的指令文件会降低指令遵循。因此，提升到这一层的内容需要保持精简：少量重要笔记直接可见，其余细节留在按需读取的文件中，并留下链接。否则，原先为了省去查找而放入的内容，会逐渐挤占处理当前任务的空间。

原文以 Claude Code 的 auto memory 说明这种分工：每次只加载 `MEMORY.md` 的**前 200 行或 25 KB**，用这个头部告诉 Claude 已有知识是什么、在哪里。它既控制注入量，也提供索引，让当前任务可以沿入口继续读取细节。这一限额属于该实现，其他系统需按自己的上下文预算安排；Claude Code 在会话内维护这层内容，而 dreaming 可以在后台承担类似整理工作，两者的执行时机不同。

到这里，上一段经验才有机会影响下一次行动：转写保留可回查的经历，笔记选择未来可能需要的内容，验证与回看纠正其中的判断，wiki 将分散内容组织成可查路径，注入再把关键内容和入口带到新会话。任何一步都可能留下缺口——猜测未经检验、页面遗漏事实，或索引虽已加载却未被使用。原文呈现的组件为这些问题分别提供了处理位置，而具体投入多少在线记录、离线整理和按需读取，仍取决于任务如何重复、环境如何变化，以及模型能否主动完成读取与检验。
